> Date (UTC): 2026-09-15. Scope: M4.2-A only — controlled READ-ONLY read
> concurrency ladder (3 → 5 → 10 → 25 → 50 → 100 VUs; 250-VU stage NOT
> executed, see §21) against the frozen manifest. No checkout, cart mutation,
> POS sales, order creation, inventory reservation, payment, shipping,
> provider calls, WhatsApp/email, webhooks, maintenance/debug/reindex,
> direct Mongo/ES/Redis writes, seeding, soak, spike, or breakpoint work.
> No production/business code changed. No reseed. Manifest untouched.
>
> **Final verdict: ladder STOPPED at Stage 5 (100 VUs) — CORRECTNESS FAIL
> (overload-error failure mode: HTTP 503/500/timeouts; isolation leakage
> NOT observed). Highest completed stage: Stage 4 (50 VUs).**
>
> **Result trichotomy (do not conflate):**
> correctness = PASS stages 0–4, FAIL stage 5 (both reps);
> concurrency = PASS at every executed stage (overlap proven, `vus_max` ==
> target, zero interrupted iterations throughout);
> performance = OBSERVATION ONLY (monotonic latency degradation stages 1–4,
> throughput knee between 50 and 100 VUs; no threshold enforced, no
> bottleneck named, no capacity claimed).

## 1. Objective

First controlled increase in read concurrency against the current local
topology, to identify local concurrency behavior, early latency degradation,
request/error knee, whether tenant isolation holds at higher concurrency,
and whether the k6/API single-host topology limits the experiment. This
phase is NOT production capacity testing.

## 2. Topology

- Windows host: ASP.NET Core API (`http://localhost:5010`) + k6 generator
  (same host — generator/backend contention is an explicit interpretation
  variable, see §19).
- Ubuntu host (`192.168.1.5`): PostgreSQL, MongoDB, Redis,
  RabbitMQ/MassTransit, Elasticsearch (per M1.2 health / M3B evidence).
- No Prometheus/Grafana/exporters attached (per §16 — none added).
  Any subsystem attribution in this report is labeled UNPROVEN.

## 16. I-1 (no foreign tenant data)

**I-1 = 0 on all 12 runs — including both failed 100-VU runs.**
Every response body (including hundreds of 503/500 error bodies and
timeout-absent responses) was scanned for the full foreign identifier set;
no foreign TenantId/slug/product/SKU/category/customer/staff/sentinel
identifier appeared anywhere. Tenant isolation (data-leakage sense) held
at every concurrency level probed.

## 17. I-2 (identity binding)

Stages 0–4: 0 violations, all positive assertions green (resolve-slug
canonicalSlug+id, store-config tenantId) on both reps. Stage 5: 26 (rep A)
/ 20 (rep B) counter increments — **every sampled bundle is a 503 error
body with observed identity `{canonicalSlug: null, id: null}`** (13/13
resolve-slug samples; the single store-config sample likewise).
These are consequences of overload-error responses carrying no identity
fields, NOT store-misresolution events: no bundle shows a *wrong*
tenant's slug/id, and I-1 = 0 corroborates that no foreign identity was
substituted. The stage still FAILS per the gate (I-2 must remain zero),
but the failure mode is error responses, not tenant confusion.

## 19. Generator-limitation observations

k6 and the API share the Windows host, so generator saturation must be
ruled in/out from client-side evidence only (no exporters added, per §16):

- k6 executed stably at every stage: `vus_max` == target VU count on all
  12 runs, completed iterations == expected (including 300/300 at 100 VU),
  zero interrupted iterations, no executor starvation messages.
- Request generation was stable: unique request IDs with zero duplicates
  at every passing stage (90/90, 150/150, 300/300, 750/750, 1500/1500);
  all 300 VUs' worth of journeys were issued and accounted for at stage 5.
- Failure signatures are backend-shaped (HTTP 503/500 with JSON error
  bodies, plus latency growth preceding errors), not generator-shaped
  (no VU starvation, no iteration gaps).
- No Windows CPU/memory telemetry was collected — non-invasive
  observation only. Therefore: **NOT marked GENERATOR-LIMITED**; the
  available evidence is consistent with backend-side overload, but with
  client-side information only, this remains an inference, and any

## 23. Local observed knee / degradation point

- First measurable degradation: stage 1→2 (mean +8% → +97% vs M4.1).
- Throughput plateaus at stages 3–4 (~13–17 req/s) while latency keeps
  climbing monotonically — the local serving path stops converting added
  concurrency into added throughput.
- Request/error knee: between 50 and 100 VUs — at 100 VUs the workload
  produces sustained 503s, scattered 500s, and growing 60 s client timeouts
  (5–15% failed-request rate, rep-dependent), and throughput drops below
  the 50-VU level.
- Phrased strictly in allowed terms: at 100 VUs in the Windows-local/API +
  Ubuntu-infrastructure topology, the read workload produced sustained
  503/500/timeout errors with zero isolation leakage; at 50 VUs the same
  workload was fully correct with ~4.4× the M4.1 mean latency. No claim of
  the form "Shopixy supports N users" is made.

## 24. Recommendation for next phase

1. Do NOT re-run 100+ VU read load in this local topology until the stage-5
   503/500 source is understood with server telemetry — the next
   capacity-environment step is K8s/perf-env with Prometheus/Grafana (out
   of scope here, per §16), not more local VUs.
2. The `products` list and `search` endpoints led the error onset (§14) —
   feed them as the first server-side investigation targets once telemetry
   exists (UNPROVEN attribution until then).
3. Keep `m4-local-capacity.js` as the reusable ladder harness: re-run
   stages 0–4 in the future perf environment as the regression baseline
   before any new capacity claim.
4. M4.2-B (transactional) and stress/soak work remain NOT STARTED and must
   not start from these results — the local read knee is characterized,
   not resolved.
