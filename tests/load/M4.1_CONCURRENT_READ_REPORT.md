## 5. Iteration count

Executor `per-vu-iterations`: `vus: 3, iterations: 10, maxDuration: 10m`.
Each VU performs exactly 10 complete journeys → **30 journeys per run**,
60 journeys total. Each journey issues 10 GETs → **300 requests per run**
(270 own-context + 30 negative probes). Confirmed: `iterations=30`,
`vus_max=3`, `M41-DONE` ×30 and `M41-CTX` ×30 per log, both runs.

Between iterations each VU takes a bounded deterministic stagger sleep,
`0.05 * ((__VU + __ITER) % 4)` seconds (0 / 0.05 / 0.10 / 0.15 s cycle):
small enough to keep all VUs overlapped, deterministic enough to stay
reproducible. No large random distribution (`Math.random` unused for sleep).

## 16. Safety evidence

- **GET-only (300/300 both runs):** `lib/http.js` throws on any non-GET
  method, so a write cannot be issued even by accident; log method census is
  `{GET: 300}` per run. In-script read-only allowlist (8 path prefixes)
  covers exactly the 10 issued request shapes; anything else `fail()`s.
- **No auth introduced:** all journey endpoints `[AllowAnonymous]`
  (verified in controllers during M4.0); seeded owner credentials untouched.
- **No forbidden operations:** static scan of `m4-concurrent-read.js` finds
  no executable checkout/cart/POS/sale/write/Mongo/ES/Redis/provider/webhook/
  payment/maintenance/debug/reindex/TestAuth constructs — the only matches
  are the scope-comment header and the `mongoVerified` /
  `elasticsearchVerified` manifest flag-name reads in `setup()` /
  `handleSummary` (flag validation, not data-plane access).
- **No seeding, no manifest/seed changes, no reseed** (manifest
  `verifiedAtUtc` identical pre/post runs; `latest.json` untouched).
- **No provider touches, no webhooks, no TestAuth, no direct
  Mongo/ES/Redis access** — the scenario only performs anonymous HTTP GETs;
  the only server-side state touched is the API's own read-cache behavior,
  same as any customer browse.
- **Writes occurred: none.**

## 18. Observations

1. Under 3-way concurrent same-shape reads, per-tenant latency is
   indistinguishable (means within ~1%), consistent with preserved
   isolation at the serving layer — an observation supporting the
   correctness verdict, not a performance claim.
2. Latency shape matches M4.0 single-VU ordering (`products` list slowest,
   then `search`, then `search-suggest`; config/categories/home/negative
   fast), now reproduced with 30 samples per endpoint per run instead of 1.
3. Run-to-run means drifted ~4% upward on run 002 with no correctness
   change; with n=30 journeys in a shared local/remote topology this is
   recorded as noise characterization, not regression.
4. `home-featured` returns `[]` (body hash `72163580:2` on all 60 reads)
   since no featured flags are seeded — a valid safe read; I-1 passes
   trivially on it.
5. Raw k6 console logs were captured via `Tee-Object` (UTF-16); the
   committed evidence is this report plus the scenario/lib files. Parsing
   accounted for the encoding and console line-wrapping; step counts
   reconcile exactly (300 steps / 30 dones / 30 ctxs per run).

## 19. Recommendation for M4.2

M4.1 is complete with a PASS verdict — proceed to M4.2 scoping with this

`m41_*`-style metric set as the template; extend only the workload mix
(e.g. authenticated reads / cart-adjacent probes) per the M4.2 brief when it
lands. No M4.2 work was started in this phase.
