# Payment Platform Architecture Violation Classification

## Scope

This report classifies the findings pasted from `PAYMENT_PLATFORM_CERTIFICATION_1` using source-level architectural judgment. It is not a new certification and does not introduce new findings.

Evidence was checked against referenced C# source locations only. Repeated metric rows and test restatements from the prior report are consolidated into the source finding they measure.

## Classification Model

| Class | Meaning |
| --- | --- |
| Class A | Critical Architecture Violation: breaks provider neutrality inside canonical platform layers. |
| Class B | Boundary Leak: architecture remains directionally correct, but provider-specific logic escaped the adapter boundary. |
| Class C | Technical Debt: not architecturally wrong, but should be cleaned up or generalized. |
| Class D | Intentional Design: expected composition, infrastructure, configuration, operational, or provider-module code. |
| Class E | False Positive: previously reported as a violation, but acceptable under the classification rules. |

## Prioritized Refactoring Roadmap

1. Remove Paymob-to-Stripe coupling by moving shared provider reference/execution types into neutral provider contracts.
2. Neutralize lifecycle contracts and lifecycle execution by replacing `StripeWebhook` and `PaymobWebhook` sources with provider-neutral gateway/callback source handling.
3. Replace the core `PaymentProvider` enum in canonical flows with a provider code/value object and provider registry.
4. Move provider credential validation out of `PointOfSale.Core.Payments` into provider modules or a provider capability registry.
5. Introduce neutral CommerceHub payment and refund gateway abstractions, then move Stripe/Paymob DTOs, SDK calls, webhook parsing, and refund API calls behind adapters.
6. Refactor Checkout to call neutral payment initiation/session contracts instead of direct Stripe, Paymob, and Fawry services.
7. Isolate Fawry checkpoint readiness behind a neutral persisted-intent/provider adapter contract.
8. Consolidate replay records and persistence into a neutral webhook replay table after an additive migration and backfill plan.
9. Clean technical debt: duplicate `CanonicalProviderError`, provider-specific comments, and hardcoded accounting defaults.
10. Re-run architecture and provider tests only after source-level Class A and Class B work is complete, then triage remaining test-environment failures separately.

## Estimated Certification Effort

Estimated effort to achieve true provider-agnostic certification: 3 to 5 engineering weeks.

The critical path is the Class A work plus CommerceHub/Checkout boundary refactors. Persistence cleanup and test stabilization may extend the timeline if replay-table migration or integration fixture repair is required.
