# PASS SF-ORD.XCHANNEL Admin Order Cross-Channel Presentation Authority Certification

2026-07-01 update: SF-ORD.XCHANNEL2 re-reviewed only PointOfSale.Web admin Order Management presentation and directly consumed admin order DTO/API/service code for multi-channel canonical contract integrity. No prior Storefront, Affiliate, Marketplace, checkout, payment, shipping, payout, commission, builder, CMS, analytics, or synchronization domain was re-certified. Runtime hardening added backend-owned `SourceOrderId` to `AdminOrderListItemDto`, maps standard list rows from SQL `Orders.SourceOrderId`, maps Marketplace list rows from SQL `CommerceHubSubOrders.MarketplaceOrderId`, and requires frontend Marketplace lineage admission to reject DTOs unless `SourceOrderId` exactly matches backend `MarketplaceLineage.MarketplaceOrderId`.

Scope reviewed: PointOfSale.Web admin Order Management runtime responsible for presenting Orders from Storefront, Affiliate, and Marketplace channels, plus directly consumed admin order DTO/API/service and frontend admission code. Storefront runtime, Affiliate runtime, CommerceHub runtime, checkout implementation, marketplace synchronization, affiliate payout, commission calculation, payment runtime, shipping runtime, Builder, CMS, analytics, and previously certified channel-specific authority domains were not re-certified.

Pages reviewed: `PointOfSale.Web/src/pages/Orders.jsx`.

Backend endpoints reviewed: `GET /api/admin/orders`, `GET /api/admin/orders/{orderId}`, and status mutation precondition impact at `PUT /api/admin/orders/{orderId}/status` only where consumed by admin Order presentation.

Backend services reviewed: `AdminOrderService.ListOrdersAsync`, `AdminOrderService.GetOrderDetailsAsync`, `AttachAffiliateAttributionEvidenceAsync`, `LoadAffiliateAttributionEvidenceAsync`, `AttachMarketplaceLineageEvidenceAsync`, `MapMarketplaceSubOrderToDetailsDtoAsync`, and admin order DTO mapping in `AdminOrderDtos.cs`.

Cross-channel findings: Storefront and Affiliate orders enter the admin presentation contract through canonical SQL `Orders`; Marketplace vendor rows enter through SQL `CommerceHubSubOrders` plus parent `CommerceHubMarketplaceOrders`. The shared admin contract is `AdminOrderListItemDto`/`AdminOrderDetailsDto` carrying backend-owned `Source`, `SourceOrderId`, `IsMarketplaceOrder`, nullable `AffiliateAttribution`, and nullable `MarketplaceLineage`. No channel bypasses the admin DTO/API/service admission path reviewed here.

Isolation findings: Storefront Orders remain Storefront. Affiliate Orders remain Affiliate through Storefront canonical order plus backend attribution evidence. Marketplace Orders remain Marketplace. A Marketplace row requires `Source = Marketplace`, `IsMarketplaceOrder = true`, and backend Marketplace lineage. A non-Marketplace row with Marketplace lineage fails closed. Affiliate evidence must match tenant/order attribution. Frontend source labels are admitted display, not identity authority.

Canonical contract findings: Backend canonicalization begins before frontend presentation and is preserved by `AdminOrderService`. Canonical Order and Canonical DTO remain backend-owned. `SourceOrderId` is now present on both list and detail DTOs where source identity exists. Marketplace list/details presentation requires source identity parity with backend Marketplace lineage. Frontend filtering, sorting, searching, selection, navigation, and rendering do not canonicalize or rewrite lineage.

Metadata isolation findings: Affiliate attribution is nullable and admitted only from SQL attribution/order snapshot agreement. Marketplace metadata is nullable and admitted only from SQL marketplace sub-order/parent order evidence. Storefront orders cannot gain Marketplace identity, Marketplace metadata, vendor identity, or external identity in presentation; Marketplace orders cannot gain Affiliate attribution in the reviewed mapping.

Recovery findings: Refresh, reconnect, application restart, Redis flush, Mongo rebuild, and projection rebuild re-enter no-store SQL-backed admin order APIs. Admin Orders does not consume Mongo projection as authority. Recovery cannot change channel identity because presentation re-admits backend DTO source, affiliate, and Marketplace lineage each time.

Cache findings: React, React Query, Zustand/auth state, LocalStorage, SessionStorage, browser cache/BFCache, Redis, Mongo, and projections are non-authoritative. Runtime hardening now re-applies strict list/detail order visibility admission inside `Orders.jsx` before rendering React Query data, so same-tenant replay or route-mismatched detail evidence fails closed at the page boundary.

Adversarial findings: Replaying Storefront DTO as Marketplace fails unless backend Marketplace source and lineage evidence are present. Replaying Marketplace DTO as Storefront fails because `IsMarketplaceOrder` and `Source` must agree. Replaying Affiliate DTO as Marketplace fails because affiliate and Marketplace evidence are independently admitted. Injected Marketplace metadata into Storefront, Affiliate attribution into Marketplace, modified source type, modified source order identity, modified vendor identity, modified referral code, or modified external order ID fails closed before presentation.

Pipeline findings: Channel begins in backend channel-specific order admission. Canonicalization begins in backend SQL/services. Authority begins at trusted tenant/session authority, Owner/Admin/Manager authorization, SQL, and `AdminOrderService`. SQL persistence begins in backend order/sub-order/attribution transactions. Presentation begins only after admin DTO emission, frontend API admission, and page-level admission in `Orders.jsx`.

Boundary review: Storefront Boundary owner is backend checkout/SQL, recovery source is SQL `Orders`, failure behavior is no Storefront presentation without `Ecommerce` source evidence. Affiliate Boundary owner is backend referral/checkout/SQL attribution, recovery source is immutable SQL order snapshot, failure behavior is no affiliate badge/details. Marketplace Boundary owner is CommerceHub marketplace SQL order/sub-order authority, recovery source is SQL parent/sub-order rows, failure behavior is no Marketplace presentation. Canonical Boundary owner is backend `AdminOrderService`, recovery source is SQL reads, failure behavior is API failure or omitted nullable lineage. Presentation Boundary owner is frontend rendering after admission, recovery source is refetch, failure behavior is fail-closed error/withholding. Recovery Boundary owner is backend SQL/service re-entry, failure behavior is no frontend reconstruction. Isolation Boundary owner is backend DTO evidence plus frontend admission, failure behavior is rejected presentation.

Runtime hardening performed: `Orders.jsx` uses `requireCurrentVendorOrderVisibilityListAuthority(ordersQuery.data, user)` and `requireCurrentVendorOrderVisibilityAuthority(detailsQuery.data, user, selectedOrderId)` before presentation, and surfaces list/detail admission failures as read errors. SF-ORD.XCHANNEL2 additionally adds `SourceOrderId` to `AdminOrderListItemDto`, maps it from SQL for standard and Marketplace rows, and rejects Marketplace presentation when DTO source identity does not match backend Marketplace lineage identity.
