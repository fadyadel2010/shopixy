# PASS SF-CMS4 CMS SEO Authority Certification

PointOfSale.Web CMS SEO is production-certifiable after focused SEO admission hardening. The inspected runtime is limited to PointOfSale.Web CMS SEO editing plus backend APIs/services directly consumed by CMS SEO editing, preview, publish, public SEO metadata, sitemap, and projection.

Pages reviewed: `CmsPageEditor.jsx`, CMS page list/editor admission helpers, CMS service calls, and CMS store candidates. Storefront was reviewed only at public CMS SEO/read/projection boundaries.

Backend endpoints reviewed: `GET/POST/PUT /api/admin/pages`, `POST /api/admin/pages/{id}/publish`, `GET /api/admin/pages/{id}/preview`, `POST /api/admin/pages/{id}/preview-link`, public CMS page reads, SEO metadata, robots, and sitemap endpoints where they consume CMS SEO/public projection.

Backend services reviewed: `CmsPageService`, `CmsPageReadService`, `CmsPageContentValidator`, `AdminCmsService`, `SeoService`, `CmsPageProjectionConsumer`, and CMS cache/projection helpers.

SEO findings: Meta Title, Meta Description, Keywords, and OpenGraph image are editable frontend candidates only. Accepted values begin only after backend tenant/session authority, Owner/Admin authorization, validation, canonicalization, sanitization, expected-version/`If-Match`, SQL persistence, and accepted DTO admission. Canonical URL, canonical slug, robots, indexability, structured data, Schema.org, sitemap membership, publication, projection, and audit are backend-owned or not admin-editable in this CMS runtime.

Canonicalization findings: slug normalization begins in `CmsPageReadService.NormalizeSlug`; CMS canonical URL generation begins in `SeoService.BuildCanonicalUrl` from backend base URL plus current published SQL slug. The frontend slug normalizer is candidate ergonomics only and cannot create canonical slug or canonical URL authority.

Structured Data findings: this CMS SEO editor has no accepted structured-data or JSON-LD mutation field. Breadcrumb JSON-LD is generated by backend SEO services for supported public routes; injected `structuredData`/JSON-LD fields in frontend DTOs are stripped or ignored and cannot persist as CMS SEO authority.

Media findings: OpenGraph image candidates are accepted only after backend safe URL validation as relative or http(s) URLs without credentials or control characters. Frontend DTO admission also rejects unsafe SEO image evidence before editor presentation.

Recovery findings: refresh, reconnect, server restart, Redis loss, Mongo rebuild, and projection rebuild recover from SQL `CmsPages` plus backend publication/projection events. Stale SEO in React, cache, Redis, Mongo, or search cannot survive as authority when current SQL no longer agrees.

Concurrency findings: duplicate saves, retry, replay, and another-admin edits must carry current expected CMS version or `If-Match`; stale versions fail with conflict/latest-version admission. Stale SEO cannot overwrite backend SEO after a newer backend version exists.

Cache findings: React, Zustand, browser cache/BFCache, LocalStorage, SessionStorage, Redis, Mongo, and search are presentation, invalidation, or derivative projection only. CMS public SEO metadata and sitemap CMS URLs recompose from current SQL.

Cross-system findings: CMS SEO becomes visible after backend publish promotes the accepted version, SQL public reads can see it, and projection/search/sitemap consumers re-enter current backend authority. Builder, Storefront, Search, SEO, Navigation, Analytics, Redis, and Mongo cannot observe unsaved CMS SEO candidates as accepted truth.

SEO pipeline: SEO Candidate begins in the CMS editor form. Mutation DTO begins in `toRequestPayload`. Backend validation/canonicalization/sanitization begin in `AdminCmsPagesController`, `CmsPageService`, `CmsPageContentValidator`, and `CmsPageReadService.NormalizeSlug`. Authority begins at backend tenant/session plus Owner/Admin authorization. SQL persistence begins in `CmsPageService` after expected-version admission and serializable mutation. Projection begins at `StorefrontCmsPagePublishedEvent` and `CmsPageProjectionConsumer` SQL recomposition. Accepted DTO begins when backend emits the saved/published CMS response. Presentation begins only after frontend CMS DTO admission hydrates editor state.

Runtime hardening performed: backend SEO text now rejects control-character injection before SQL persistence; frontend CMS page DTO admission now validates supported SEO fields, rejects unsafe SEO image evidence, and strips unsupported canonical/robots/structured-data/Twitter-style SEO authority fields by construction.

Exact runtime files modified: `PointOfSale.API/Services/Cms/CmsPageService.cs`, `PointOfSale.Web/src/modules/storefront/cms/cmsPageIdentityAuthority.js`.

Regression freezes added: `PointOfSale.Tests/Cms/CmsPageWorkflowTests.cs`, `PointOfSale.Web/src/modules/storefront/cms/cmsPageIdentityAuthority.test.ts`, and `PointOfSale.Tests/Architecture/CmsSeoAuthorityCertificationTests.cs`.

Architecture documentation updates: all five authority context files include PASS SF-CMS4, and this findings document records the boundary.

Certification answers: frontend cannot create accepted SEO; React, LocalStorage, Redis, Mongo, search, replay, injected canonical URL, injected JSON-LD, injected robots, and stale DTOs cannot become CMS SEO authority. Meta Title, Meta Description, Canonical URL, Canonical Slug, Robots, OpenGraph, Twitter Cards, Structured Data, Sitemap, SEO Images, and Published SEO are backend-owned. CMS SEO is production-certifiable.
