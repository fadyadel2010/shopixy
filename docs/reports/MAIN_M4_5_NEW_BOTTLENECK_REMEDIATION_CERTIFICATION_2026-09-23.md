### Acquisition, cache and security details

The product cache remains an owned, generation-fenced Redis **candidate** cache. `RedisJsonCacheService.GetOrCreateCoreAsync` rechecks the value after its keyed distributed lock, then invokes the factory (including SQL) while holding the refresh lock. A Redis hit never takes the factory shortcut and is recomposed from SQL; when Redis is disabled/unavailable or a result is skipped/not found, cross-request SQL work is **not** coalesced. No in-memory unbounded authority cache was added. For the slug-based detail path, the cold factory now rejects a SQL-authorized product whose *current* slug differs from the requested slug, matching the former second-pass validation and avoiding caching it under an incorrect slug. The product query remains tenant-filtered; the home snapshot is tenant-filtered and its lineage lookup rejects missing/deleted/foreign ancestors. The existing tenant/domain generation, invalidation, negative cache, Redis startup validation and shared multiplexer were not changed.

The publication guard still performs one SQL StoreConfig/Tenant join for guarded anonymous GET/HEAD routes, except exact `/api/storefront/store-config`. The domain resolution result establishes active tenant authority but carries **no** StorefrontStatus. Eliminating this join by accepting Redis domain authority would expose unpublished shops; a cross-request publication cache would require transaction-correct StoreConfig invalidation absent from the existing domain-generation dependency graph. No publication-cache claim is made. Authentication/host tenant mismatch continues to be rejected upstream. Store-config still joins active, non-deleted Tenant with tenant-owned StoreConfig; its separate global ThemePreset query selects preferred key before `default`. The two reads are independently mutable; blindly merging/caching themes could alter fallback and invalidation behavior.

Slug resolution continues to read a raw Redis candidate then check product/category/CMS SQL authority; negative misses are not cached/coalesced and the raw slug key has no generation-fenced ownership for all three mutation families. Warm candidate SQL revalidation therefore cannot safely be removed. Its product branch shares the SQL overlay and therefore saves the same one tenant-query acquisition on a positively resolved product. Search uses an already set-based product overlay (tenant SQL predicate inside chunked products and ancillary domain batches); home product shelves also recompose cached cards in a SQL batch. `StorefrontSearchController.FilterSearchItemsBySqlAuthorityAsync` still has a separate tenant activity check before its product overlay, required for category/CMS-only result sets; consolidation there remains unproven. Query counts for those specific MAIN HTTP routes were **not** captured here, so neither a measured per-route total nor end-to-end runtime reduction is claimed. Redis operations per route depend on host cache state and owned-cache lock retries; no runtime count was measured.

Cart GET still looks up tenant/cart-scoped `StorefrontCartCouponStates` even when Redis indicates no coupon. That persisted record can be newer than the Redis cart; skipping the lookup would allow stale or incorrect discounts. Coupon revalidation can then acquire more SQL authority. The lookup is not proven redundant with promotion evaluation, and no financially unsafe cache was introduced. `CartService` still locks by owner (merge locks sorted), renews and token-releases; cart load, identity and cumulative stock checks, validation/recalculation and Redis persist remain within the lock. The earlier event batch is staged outside the lock; `MassTransitEventPublisher` conditionally flushes once per batch and detaches newly staged outbox entries on staging failure. Removing this flush or shifting it to an unawaited task would risk lost messages. No new lock interval measurement or outbox failure regression was added in this pass; **lock interval before/after is unchanged**, and lock-hold minimization is not certified.

Pool policy is unchanged (`PostgresConnectionStringPolicy`: defaults 15-second connection and 30-second command timeouts; no MaxPoolSize override; non-pooled one-shot health probes). `Program.cs` registers the application `UseNpgsql(defaultConnectionString)` and configures MassTransit EF outbox from that normalized string. This is a source inspection, not proof of actual deployment connection-string equivalence across Hangfire/background contexts. `CommerceHubCheckoutService.Create` starts a Serializable transaction before authority service calls and inventory reservations (`CommerceHubCheckoutService.cs:401–805`); whether all nested awaits hold a PostgreSQL connection while waiting on unrelated dependencies requires a call-graph/occupancy audit before changing transactional boundaries. The whole-solution connection/transaction audit required by the request is **not complete**. No connection-occupancy improvement is claimed.
