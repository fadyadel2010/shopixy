`MongoWaitQueueFullException` semantics (driver docs, TEST-PROVEN citation class via
published FAQ): thrown on the **client**, at **connection checkout**, when in-use
connections = `MaxConnectionPoolSize` AND the bounded wait queue is full — i.e. **before
any byte reaches the server**. It is by construction a client-capacity signal, never
proof of server saturation.

1. **Negative lookups never cached** — `RedisJsonCacheService.PopulateCacheAsync:506-509`:

   Every sentinel/foreign/miss probe (negative-read, negative-write, resolve-slug miss,

   any negative probe; SECOND READ: the identical next probe; WHY: null-guard skips

2. **Category-tree list path bypasses Redis** — `StorefrontProductsController.

5. **No same-request double-read of the same product on hot M4.5 paths** — add/update/

## 18. Primary root cause

**MongoDB client connection-pool / wait-queue capacity (A).** The single shared driver's
primary pool (100 connections, ~500 computed waiters, `MaxConnecting` 2, all defaults)
cannot carry the application's 6000-VU concurrent Mongo read demand; checkout refuses
with `MongoWaitQueueFullException` before any server execution, surfacing as products
503s and the cart-404/state-transition cascade. Proven by single-mechanism elimination:
pool 100→200 alone → zero exceptions, healthy server throughout, 20x fewer failures.

## 19. Secondary contributors

- **(B) Excessive application-generated concurrent Mongo demand — YES (secondary).**

  slug reads, and an uncached category-tree path, all of full documents, against one
  100-connection primary pool. Residual 663 failures + 2.27 s median at pool 200 show
  demand pressure persists past the first bottleneck.
- **(C) Duplicate/repeated reads — YES (patterns CODE-PROVEN, quantitative share
  UNPROVEN).** Uncached negatives, uncached category-tree lists, unprojected documents.
- **(D) Slow Mongo operations — UNPROVEN, evidence weighs against.** No slow-op capture
  exists; server telemetry shows no execution-side pressure at any window.
- **(E) Server saturation — NO (ruled out).** During-load tickets full, WT/memory flat,
  post-storm idle; per-node data limited to `mongo-0` + member list (secondaries'
  `serverStatus` not sampled — disclosed gap, immaterial since all reads are primary).
- **(F) Pool fragmentation — NO (ruled out).** One client, one pool per server.
