## 17. Evidence for/against the causal chain

`PER-REQUEST TENANT PG RE-PROOF → PRE-ENDPOINT PG DEPTH → ADMISSION PRESSURE →
QUEUES → 503/TIMEOUT/CASCADE`: A1 removed the first link (LOAD-PROVEN: authority
≈ 0, leg at clean level). Downstream, Kestrel queues collapsed to burst-transient
and 5xx onset moved +29 s → +90–100 s (LOAD-PROVEN). But the terminal failure
boundary did not decrease because MongoDB wait-queue saturation (an independent,
previously-predicted downstream link — A1 report §18) now binds first, driving
products 503s and the cart-404/state-transition cascade. The chain after the
tenant link is re-routed through Mongo, not through Kestrel/PgBouncer admission.

## 18. A1 hypothesis verdict

**MECHANISM REMOVED BUT NOT SUFFICIENT** (equivalently: A1 SUCCESSFUL + NEW
DOWNSTREAM BOUNDARY — not "A1 failed").

- ACCEPT requires tenant move + queue move + failure decrease. Rules 1–3 are met
  directionally (tenant ≈ 0; Kestrel transient-only; onset delayed), but rule 4
  fails: R1 failures (1,734) essentially equal the baseline (1,633) with the same
  cascade shape, and R2 (3,418) is worse.
- The middle rule applies verbatim: tenant work clearly decreased and legs clearly
  improved, BUT the 6000-VU failure boundary remains essentially unchanged.
- REJECT is excluded: tenant phases did not remain high, authority work did
  decrease, queues did move, and the improvement is in the predicted mechanism —
  none of the rejection conditions hold.
- Per the task: STOP THERE. No further optimization was stacked into these runs.

## 19. What A1 definitely improved (LOAD-PROVEN unless noted)

- Per-request tenant-authority PostgreSQL re-proof eliminated for warm keys
  (authority p50 0.01 ms at 3000 and 6000 VU; request leg p50 0.05 ms).
- Kestrel admission queues reduced from sustained to burst-transient (max 37 at
  3000; 225/1,018 single-burst samples at 6000).
- Sustained-5xx onset delayed from +29 s to +90–100 s.
- 3000-VU latencies improved past the clean baseline (med 289 vs 444 ms; p95
  1,998 vs 3,027 ms; p99 4,538 vs 7,292 ms) with clean steady state.
- Correctness semantics intact: I-1 0, duplicates 0, malformed 0 (R2), negatives
  behave as designed (expected 404s), no tenant-isolation signal anywhere.

## 20. What A1 did NOT improve (by design or by evidence)

- Publication per-request PG verdict (unchanged code; now the dominant
  pre-endpoint depth).
- MongoDB read-path capacity (products/cart validation) — the binding 6000-VU
  boundary (4,690/3,573 wait-queue exceptions).
- The 6000-VU failure boundary: 503 volume, cart-404 cascade, state-transition
  failures, and (R2) 60 s timeouts persist or worsen.
- Negative-verdict requests still cost one PG proof each (fail-closed, by design).

## 21. Whether the next bottleneck is now identifiable

Yes — LOAD-PROVEN, not inferred: MongoDB connection wait-queue saturation in the
products/cart read paths (`CartService` product-validation reads first,
`StorefrontProductsController` list reads second). Secondary: publication
per-request PG depth (p50 219 ms at 6000). Tertiary watch: Npgsql usage peaks
(~6,000/10,000) if Mongo is unblocked next.
