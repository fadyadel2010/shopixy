# MAIN — Arabic SKU and Product Media final certification (2026-09-24)

## Verdict

**PASS for the two reported workflows on the local authenticated stack.** Arabic product and variant SKUs were read back after saving and are distinct across products and within the variant matrix. JPG, PNG, and WEBP were uploaded from the Product Edit UI, registered with HTTP 201, read back from product media, and rendered after refresh. This is a local-development verification; it is not a production R2 deployment certification.

## 1. SKU root cause and complete path

- `ProductForm.jsx` suggests the product slug from the name; the backend owns tenant-unique slug persistence. A slug is **not** an SKU. Simple identity is authored in the same form; a blank SKU is resolved by `ProductVariantCloneImportAuthority.ResolveUniqueSkuAsync` during product authoring. Its old `AUTO-{productId:N}` expression truncated the GUID to eight digits; distinct products with a shared leading eight-digit segment could get the same fallback.
- On the variant tab, `ProductForm.jsx` passes `formData.name` as `productSkuPrefix` to `ProductVariantsTab.jsx`. The frontend's ASCII-only `normalizeSkuPart` removed Arabic text. The old `buildSkuForRow` substituted literal `VARIANT`, and within-matrix collision handling appended `-2`, `-3` without checking other products. Arabic names containing ASCII numbers could instead generate the same numeric prefix for multiple products.
- `ProductForm.jsx` sends the simple SKU or the authored variant matrix to `POST/PUT /api/products`. The product authoring orchestrator checks intra-request and other-entity SKU ownership in the tenant; the PostgreSQL indexes `IX_Products_TenantId_SKU` (live product) and `IX_ProductVariants_SKU` (live current semantic variant) enforce within-table uniqueness at commit. Cross-table uniqueness is checked in application code; the two indexes do not jointly prevent an inter-table race. Server conflict responses are typed `PRODUCT_SKU_CONFLICT`. `ProductVariantsTab` and Product Edit display returned SKUs; POS catalog/checkout use product or variant SKU as appropriate.
- Existing English default variant generation and English variant patterns remain as before. Product-level simple SKU generation now exposes a button; saving a blank simple SKU still uses the server's `AUTO-<full product GUID>` fallback.

## 2. SKU implementation, scope, collisions and evidence

- `productSku.js` derives an ASCII `PX-<32 uppercase GUID hex digits>` namespace from the persisted product ID (or a stable cryptographic draft UUID), then `-V01`, `-V02`, etc. for variant rows. Names containing non-ASCII characters—including Arabic plus ASCII numbers—use this namespace. English variant prefixes/patterns retain existing behavior. The simple Generate SKU button uses an English name when usable and the product namespace otherwise; no Arabic is embedded.
- The simple server fallback now uses the **whole** product GUID, and its existing tenant-scoped ownership loop tries a numeric suffix when it finds a collision. Product authoring retains PostgreSQL uniqueness and typed conflict handling. For generated `PX-` values, the frontend catches a server `PRODUCT_SKU_CONFLICT`, generates a fresh namespace, and retries with a **new idempotency key**, at most three attempts. User-authored SKUs and other failures do not silently change. A form retry updates the displayed candidate. The in-memory matrix catches duplicate rows before save; server/database remain authoritative. These UUID-derived values are not a substitute for server checks.

## 3. Upload 400: exact request, contract and root cause

- The **file** is posted as `POST /api/upload` with browser-generated `multipart/form-data; boundary=…`, fields `file` (filename, binary bytes, browser MIME), `entityType=product`, `entityId=<product GUID>`; the Axios client supplies credentials and CSRF/tenant-bound authentication. One file is uploaded per request, sequentially for multiple selections. Server `UploadController.Upload([FromForm] UploadRequest)` validates required fields, extension/MIME/signature with `FileValidationProfiles.ProductMedia`, then 10 MiB images / 100 MiB video, stores via `IR2StorageService` in `tenants/<tenant>/products/<product>/`, and returns `{url,fileName,contentType,size}`.
- The failing request at **ProductMediaManager.jsx:241** was **not multipart**. It was the subsequent `POST /api/admin/products/{productId}/media` with `Content-Type: application/json` and `{url,mediaType,provider}`. The media controller binds `[FromBody] CreateProductMediaRequest` and requires an `Idempotency-Key`; `ProductMediaService` checks the image URL extension and product tenant ownership before persisting media, publishing projection events and returning HTTP 201. Frontend previously omitted the required idempotency key. More importantly, local development object storage returns **`url: null`**, so the frontend submitted a missing URL to the media controller. The `[ApiController]`/request-normalization validation rejected `request.Url` before persistence. An authenticated reproduction with `mediaType=image` and no URL returned HTTP 400: `{ "code":"VALIDATION_ERROR", "message":"The request payload is invalid.", "data":{"request.Url":["Value is required."]} }` (trace ID omitted). This is contract/validation failure, **not** an invalid multipart field, file signature, or authorization denial. Both missing URL and idempotency header needed correction; supplying only the header would still fail validation.
- The canonical storage service now returns a product-media URL when storage has no public URL: `/api/upload/product-media/{productId}/{generatedFilename}`. The authenticated GET at this path checks a registered media row, its product and the current tenant, then reads bytes from **the existing `IR2StorageService` object key**. Production R2 public URLs remain unchanged. It returns 404 for missing/foreign media. Media POST/DELETE/reorder and YouTube POST now send distinct idempotency keys. Upload updates the gallery per successfully registered file, including partial multi-file success; repeated uploads and reloads work. The UI checks MIME, extension and maximum size before upload; the backend still verifies actual signatures/limits. Validation details are shown instead of a generic invalid-payload message where supplied.

### Remaining limitations

No claim of production R2/public-CDN behavior, MP4 media runtime, real two-writer PostgreSQL conflict race, or cross-tenant authenticated browser uploads. The SQL indexes enforce uniqueness independently for products and variants, while cross-table race handling still relies on server ownership validation and typed client retries.
