## P1-A — recovery reconciliation

A recovered outer claim currently prepares against current product state before item execution. If the original per-product mutation committed but the process died before outer completion, preparation/execution can now classify that item `NOT_FOUND` (notably Delete) or `CONCURRENCY_CONFLICT` before invoking product authoring and therefore before consulting the durable per-product mutation result. The recovered outer aggregate can permanently store a result contradicting the committed mutation.

Implement a narrowly scoped reconciliation mechanism so that, for each item owned by a recovered/new outer execution, a durably completed **accepted/committed** per-product authoring idempotency result for the deterministic bulk item identity is consulted before preparation-derived `NOT_FOUND`/`CONCURRENCY_CONFLICT` (and any other current-state short circuit that would contradict that accepted mutation). It must produce a processed/reconciled bulk item result and must not invoke/mutate product authoring again. Tenant, operation, outer key, product identity, completion status, and serialized result must be validated fail-closed. A missing, incomplete, malformed, conflicting, rejected, or non-accepted per-product record is not proof of a committed mutation: current validation/business semantics remain authoritative in those cases.

Do not redesign idempotency or add a table/migration. Reuse the existing deterministic per-product key derivation and the existing `ProductRequestIdempotency` storage. Keep private/security-sensitive validation errors non-disclosing.

Add focused tests proving at minimum:

- recovered Delete where the product is now filtered/not found but its per-product accepted result is durably stored returns a processed item and exact outer replay, without a second mutation;
- recovered non-delete operation where current row version now conflicts but its per-product accepted result is durably stored returns a processed item and exact outer replay, without a second mutation;
- no completed accepted per-product mutation (missing, incomplete, malformed, or rejected as practical) preserves current NOT_FOUND/CONCURRENCY_CONFLICT behavior.

## P1-B — lease heartbeat

Renewal currently occurs only before each item. A legitimate single item taking longer than 90 seconds can be taken over while still running.

Implement an active periodic heartbeat for the entire owned execution, including while one item authoring call is awaiting. Use an interval safely below the 90-second lease (for example one third). It must start only after this execution owns the outer claim, remain active through item processing and aggregate persistence, and be stopped/awaited/disposed deterministically on every exit.

Concurrency/fencing requirements:

- Do not run concurrent EF operations on the lifecycle service's scoped `ApplicationDbContext`; heartbeat renewal must use an independently safe context/scope or an equivalently safe small infrastructure primitive.
- Renewal remains an atomic compare-and-swap using the current ownership token. Serialize token updates so heartbeat, completion, and failure finalization cannot race in-process.
- If renewal reports lost ownership or fails such that ownership can no longer be guaranteed, the execution must not successfully complete or fail the recovered claim. Cancel/interrupt item work where possible and surface `BulkIdempotencyLeaseLostException` (or the existing equivalent). The stale owner must never overwrite the successor.
- A stale worker after takeover cannot renew, complete, or finalize failure.
- Tests must be deterministic/fast (injectable/fake timing or a small test lease/heartbeat interval); do not wait 90 real seconds.

Add focused tests proving at minimum:

- heartbeat renews while a single authoring call remains blocked longer than the lease, preventing takeover;
- after simulated takeover/lost renewal, stale execution cannot complete, fail, or renew the claim;
- heartbeat stops after completion/error and does not continue touching the claim.

## Required invariants

```text
same tenant + same key + same semantic request -> replay
same tenant + same key + different semantic request -> conflict
committed per-product mutation + outer claim recovery -> recovered item result reflects committed mutation
no committed mutation -> current validation semantics remain authoritative
live long-running item -> outer lease remains owned by current worker
stale worker after takeover -> cannot complete, fail, or renew the recovered claim
recovered batch -> cannot permanently replay a result that contradicts committed product mutation
```
