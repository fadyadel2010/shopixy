# Generic shipping webhook claim protocol — design before implementation

2026-10-12. Source-only proposal; activation and relational certification are blocked.

## Selection

Keep the existing inbox/audit table and unique identity indexes. Add a separate append-per-generation `ShippingWebhookClaims` table. Absence of a claim means **legacy**, never an invitation to manufacture generation 1. Only a newly inserted log and its first claim may be committed together. Default-disabled `Shipping:WebhookClaims:Enabled` preserves containment and does not query the new table while disabled. PostgreSQL is the only supported enabled provider; ambient transactions are refused.

An expiry is permission to *attempt* fencing, not proof of process death. Every acquisition/renewal/failure locks the existing inbox row with `FOR UPDATE NOWAIT`. The authoritative business transaction locks **order → shipment → inbox**, verifies the latest generation and unique owner, and retains that inbox lock through all state, lifecycle, collection and scoped transactional outbox writes and completion. A paused worker holding that lock cannot be reclaimed even after expiry. A paused worker outside the transaction may be superseded but cannot subsequently pass the locked owner check. Database disconnection rolls back business work and releases the lock. Availability is deliberately sacrificed for a indefinitely paused transaction; no unsafe timeout-based forced takeover.

## Identity and state

Claims carry log ID, tenant, increasing bigint generation, random UUID owner, database-clock acquisition/lease/finish times, outcome and bounded failure evidence. Generations are allocated under the inbox row lock, with a composite primary key and per-log owner uniqueness. Older generations remain audit evidence. Claim operations also verify tenant/carrier/event/hash plus shipment/order identities against the inbox. Event identity takes precedence over payload-only lookup, and payload-only identity disagreement is rejected, not collapsed to Completed.

Renewal is conditional on latest generation/owner/Processing and an unexpired lease. Recovery is conditional on a latest protocol-owned Processing claim whose lease expired, or protocol-owned Failed claim (failure writer can run only after disposal/rollback of the owned business transaction). Inbox Pending, legacy Failed/Processing, inconsistent claim/log outcomes and missing historical claims all fail closed. Completion may occur after lease expiry **only while retaining the transaction lock acquired with a valid lease**; reclaim cannot overtake it. There is no heartbeat thread or shared-DbContext concurrent access; renew immediately before entering the business transaction, which supplies stronger transaction-lifetime exclusion.

## Transaction ordering and crash boundaries

1. Validate current tenant, carrier, target, trust and integrity before admission. New admission commits log+generation 1 atomically. Racing inserts are resolved by existing database unique constraints; failed insert transactions are disposed before identity lookup. No effects before durable ownership.
2. Existing protocol retries use a short ReadCommitted acquisition transaction: lock inbox NOWAIT, re-read identity/status/latest claim, conditional insert next generation, conditionally transition Failed→Processing without clearing historical error/trust evidence, commit. Active contention returns non-success.
3. Renew via a separate short locked transaction. Begin owned business transaction; reload order/shipment using established locks, lock inbox NOWAIT and verify latest owner with database clock. Revalidate target and trust under configuration lock. No external carrier operation belongs in this transaction.
4. Finish latest owned claim conditionally and persist terminal log with all business effects and configured MassTransit bus-outbox writes in that same transaction. Intermediate fulfillment SaveChanges participates in the outer transaction; it cannot commit independently.
5. Dispose failed/ambiguous business transaction before failure persistence. Clear tracked partial work. Use independent bounded 5-second token; locked conditional update of latest owner+Processing claim and inbox only. Terminal Completed/Skipped cannot be downgraded; superseded owner cannot append a false failure for current work.

Crash before admission: nothing durable. Crash after admission/before business: expired protocol claim can be fenced. Crash during business: database rollback or still-held lock; respectively recoverable or unavailable, never concurrent commit. Commit with lost acknowledgement: Completed and effects/outbox committed together; failure CAS is a no-op and redelivery returns terminal duplicate. Failure audit crash: either Failed committed atomically or Processing remains and becomes recoverable; historical generation retained. Acquisition acknowledgement loss strands only a protocol claim, safely recovered after expiry. Any uncertified alternate writer of the inbox/claim tables invalidates this proof and must be excluded at rollout.

## Compatibility / rollout

Additive table only; no existing index changes, status backfill or historical owner assignment. Disabled runtime uses old schema safely. Narrow Bosta money-observation transaction remains separate and unchanged, with no claim backfill. Legacy reconciliation requires separately authorized fleet quiescence and per-event review of original identity/trust and domain/collection/outbox evidence, followed by an explicitly designed audited reconciliation procedure; this change offers no replay/reset endpoint. Never edit statuses by SQL to opt legacy records in.

Before enabling: review migration/schema history read-only; build separate artifacts; execute actual PostgreSQL concurrency, rollback, failure-injection and scoped MassTransit outbox regressions in an explicitly authorized safe test target; review the diff and all writer paths; separately authorize migration and coordinated fleet deployment/enablement. This task does none of those activation actions. Synthetic or metadata tests cannot certify recovery.

## Implementation review notes

Source now implements the proposal in `ShippingWebhookClaimProtocol` and the generic handler; proposed migration is `20261012160000_ShippingWebhookOwnerClaims`. The helper owns generation-1 inbox insertion and refuses persisted legacy rows or unrelated dirty effects; completion requires the fence's EF transaction identity as well as the database owner/generation CAS. Enabled business transactions use PostgreSQL ReadCommitted plus explicit order→shipment→inbox locks, following tracking/observed-collection patterns and avoiding stale Serializable admission snapshots. Locked trust evaluation remains inside `CarrierIntegrationAuthority`, using the exact locked configuration snapshot. Failure persistence is after transaction disposal; explicit manual-fulfillment rejection is a deliberate no-effect denial committed with failed claim/log, not a failure of an effects transaction.

Writer audit also found the standalone `Infrastructure/Scripts/RedactExistingWebhookData.sql` maintenance script: it can delete legacy inbox identities and redact audit fields. It is not an application runtime caller and was not run. Its age-based deletion must remain prohibited during rollout; the new restrictive claim FK prevents deletion of claimed inboxes but does not authorize deleting legacy identities. Retention needs a separately reviewed permanent-idempotency/tombstone procedure. The Bosta observed-money writer does not supersede generic claims: its independent, order/shipment-locked transaction inserts only terminal observation identities; any unique conflict rolls back its effects, and it never rewrites a generic inbox. Source evidence is not relational certification; see the closure report for executable/unexecuted counts and remaining gates.
