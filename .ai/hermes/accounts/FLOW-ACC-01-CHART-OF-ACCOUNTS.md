## 0. Critical Orientation: Two CoA Models Exist

This is the single most important architectural fact and resolves apparent contradictions in the codebase:

**A. Canonical Chart of Accounts (AUTHORITATIVE LEDGER MODEL)**
- Entity: `Account` → table `LedgerAccounts` (`AccountConfiguration.cs:14`).
- Drives the double-entry General Ledger (`JournalEntry`/`LedgerEntry`) and all financial statements.
- **Backend-only**: created by a seeder, mutated only by the posting engine, read by reports. There is **NO create/update/delete API and NO POS-Admin UI** for `LedgerAccounts` (verified: no controller references `LedgerAccounts`; no `.tsx`/`.ts` UI references `ChartOfAccounts`/`LedgerAccounts`).

**B. Legacy `FinancialAccount` model (SHADOW/DEPRECATED)**
- Entities: `FinancialAccount` (`PointOfSale.Core/Entities/FinancialAccount.cs`) → table `FinancialAccounts`, and `FinancialTransaction` (`PointOfSale.Core/Entities/FinancialTransaction.cs`).
- Has its own CRUD controller (`FinancialAccountsController.cs`) with soft-delete (`!a.IsDeleted`), `AccountNumber`, and a separate `FinancialTransactions` table.
- It is **NOT** the source of truth for balances. The authoritative reports and the posting engine read from `LedgerAccounts`/`LedgerEntries`, not from `FinancialAccounts`/`FinancialTransactions`.
- It is treated here as a parallel/legacy structure and is called out wherever it diverges. The remainder of this document focuses on model A unless explicitly noted as "legacy".

> Status legend used throughout: ✅ Implemented · 🟡 Partially Implemented · ❌ NOT IMPLEMENTED.

## 1. Executive Summary

**What is the Chart of Accounts?**
A per-tenant collection of `Account` nodes (table `LedgerAccounts`) forming a self-referencing hierarchy. Each node is a T-account in the double-entry ledger. There is no aggregate-root `ChartOfAccounts` class — "the chart of accounts" is the set of `Account` rows for a tenant, seeded from `SystemAccountTemplates` (`SystemAccountTemplate.cs`) and enforced by `AccountConfiguration`.

**What does an Account own?**
- Identity: `TenantId` (owner), `AccountCode` (immutable), `Name`/`NameAr`/`Description` (mutable), surrogate `Id`.
- Classification: `AccountType` (immutable), `NormalBalance` (derived, never stored).
- Hierarchy: `ParentAccountId`, `SubAccounts`, `Level`.
- Balance: `CurrentBalance` (denormalized, maintained by the engine; set via `ApplyEntry`/`SetOpeningBalance`).
- Flags: `IsSystem`, `IsClearing`, `PreventNegative`, `IsActive`.
- Clearing metadata: `ClearingSourceType`, `ClearingSourceCode`, `ExpectedSettlementDays`.
- Audit: `CreatedAtUtc`, `UpdatedAtUtc`.

**What does an Account NOT own?**
- It does **not** own ledger entries. `LedgerEntry` is a separate aggregate that references `AccountId` (`LedgerEntry.cs:35-36`).
- It does **not** own journals. `JournalEntry` is a separate immutable aggregate (`JournalEntry.cs`).
- It does **not** own posting logic (that lives in `FinancialPostingService`).
- It does **not** own financial statements — those are recomputed read models in `FinancialReportService`.

**Who owns financial truth?**
The **General Ledger** owns financial truth. `CurrentBalance` is a denormalized cache; the authoritative balance is the sum of `LedgerEntry` rows (`Account.cs` invariant, line 14). Reports read exclusively from `LedgerEntries` (`FinancialReportService.cs:19` — "Ledger is the ONLY source of truth"; implements `ILedgerOnlyService`).

**Is the Chart of Accounts mutable?**
Identity fields are immutable after creation (`AccountCode`, `AccountType` — `Account.cs:12-13`). Names/descriptions/flags are mutable. Accounts are **never deleted** in the canonical model (no delete path exists). System accounts are protected from rename/delete (`Account.cs:15`).

**What is the source of truth?**
PostgreSQL `LedgerAccounts` + `JournalEntries` + `LedgerEntries`. Cross-tenant isolation is enforced by `TenantId` on every row plus `ITenantContext.RequiredTenantId` enforcement.

## 4. Account Ownership (evidence-based)

**Belongs to an Account (mutated only through its own methods / seeder):**
- Identity & classification — `Account.Create()` (`Account.cs:208-238`) sets `TenantId, AccountCode, Name, AccountType, ParentAccountId, IsSystem, IsClearing, PreventNegative, Level`.
- Denormalized balance — `ApplyEntry` (`:112`), `ReverseEntry` (`:127`), `SetOpeningBalance` (`:135`) are the **only** mutators of `CurrentBalance`. They are invoked exclusively by the posting engine inside a transaction. (`Account.cs:110` "INTERNAL USE ONLY - called by posting engine within transaction".)
- Flags & names — `IsSystem/IsClearing/PreventNegative/IsActive` are public settable properties; `Name/NameAr/Description` are mutable. `SetAccountCode`/`SetAccountType` exist **only for EF materialization** (`Account.cs:243-254`).

**Does NOT belong to an Account (owned by other aggregates/services):**
- Ledger lines → `LedgerEntry` aggregate (references `AccountId`).
- Journals → `JournalEntry` aggregate.
- Opening-balance *transactions* → these are journals (e.g. `PostSupplierOpeningBalanceAsync` posts to `SupplierPayables` + `OpeningBalanceEquity`, `CommerceAccountingService.cs:423-496`). The account's `CurrentBalance` is then updated by the engine as a side effect; the *account* does not own the journal.
- Financial statements → `FinancialReportService` (read models over `LedgerEntries`).
- Posting rules / treasury authority → `FinancialPostingService` (`ValidateTreasuryInflowAuthorityAsync`/`ValidateTreasuryOutflowAuthorityAsync`, `FinancialPostingService.cs:614-861`).

## 5. Account Lifecycle

Implemented stages (all backend, no user UI for canonical accounts):

1. **Create (Seed)** — `TenantAccountSeeder.SeedAccountsAsync` (`TenantAccountSeeder.cs:49-136`) iterates `SystemAccountTemplates.All`, skips existing codes, creates via `Account.Create(...)`, sets `IsSystem=true`. Triggered by:
   - Tenant provisioning (`TenantRegistrationService`),
   - `POST /api/admin/accounting/seed` (`AdminAccountingController.cs:39-49`),
   - `ChartOfAccountsStartupSeeder` background service on app start for all active tenants (`ChartOfAccountsStartupSeeder.cs:33-91`, idempotent).
2. **Edit (names/flags only)** — `Name/NameAr/Description` and flags are mutable properties. ⚠️ There is **no API/UI** to edit canonical `LedgerAccounts`; edits would have to be direct DB or a new service. `AccountCode`/`AccountType` are immutable.
3. **Activate / Deactivate** — `IsActive` flag exists and is enforced at posting (`FinancialPostingService.cs:148-152`). ❌ No API/UI toggles `IsActive` for canonical accounts (legacy `FinancialAccount` has `PUT` but is a different model). Status: 🟡 flag implemented, toggle NOT implemented.
4. **Use In Journal** — posting engine references `AccountId` on each `LedgerEntry` (`FinancialPostingService.cs:126-145` locks/loads accounts ordered by Id).
5. **Lock** — No explicit "locked" state. Immutability is achieved via: (a) journals are immutable (`JournalStatus` only Posted→Reversed); (b) `Account` uses PostgreSQL `xmin` optimistic-concurrency token (`AccountConfiguration.cs:93-96`); (c) `LedgerMutationScope.Authorize()` restricts balance mutation to the posting engine (`LedgerMutationScope.cs`).
6. **Archive / Delete** — ❌ **NOT IMPLEMENTED** for canonical `Account`. No delete method, no soft-delete, no archive state. System accounts explicitly cannot be deleted/renamed (`Account.cs:15`). (Legacy `FinancialAccount` implements delete with guards for sub-accounts and existing transactions — `FinancialAccountsController.cs:170-203` — but that is the shadow model.)

## 6. Aggregate Analysis

```
Tenant
 └── Chart of Accounts (logical set of Account rows; no root entity)
      ├── Account aggregate           (identity, hierarchy, flags, denormalized balance)
      │    └── references ParentAccount (same aggregate type, self-ref)
      ├── Journal aggregate           (JournalEntry + LedgerEntries, immutable)
      │    └── LedgerEntry references AccountId (cross-aggregate reference, not ownership)
      ├── TreasuryAccount aggregate   (operational cashbox/bank/clearing wrapper → AccountId)
      └── AccountingOutboxMessage     (event; triggers posting)

Read models (NOT aggregates, NOT persisted):
      └── TrialBalance / P&L / BalanceSheet / CashFlow / ClearingAging / GeneralLedger
           (recomputed from LedgerEntries every request — FinancialReportService)

Separate CommerceHub financial store (NOT the tenant ledger):
      └── CommerceHubFinancialTransaction  (CommerceHubFinancialLedgerService)
```

**Ownership:**
- **Account identity / hierarchy / flags** → `Account` aggregate.
- **Posting / journal immutability / balance math** → `FinancialPostingService` (owns the posting transaction).
- **Ledger truth / balances** → `LedgerEntry` + `JournalEntry` (General Ledger).
- **Trial balance / statements** → `FinancialReportService` (read-only derivation).
- **Treasury operations (transfer/deposit/settle)** → `TreasuryTransferService` (builds `PostingRequest`, delegates to posting engine).
- **Seeding** → `TenantAccountSeeder` / `ChartOfAccountsStartupSeeder`.
- **Resolving accounts by code** → `AccountResolver` / `IAccountResolver` (`AccountCodes` constants).

The Chart of Accounts does **not** own accounting transactions — the **Ledger** owns them.

## 7. Account Behavior

**Create** — `Account.Create` factory enforces non-empty `AccountCode`/`Name`, upper-cases code, sets `Level = parentAccountId.HasValue ? 2 : 1` (`Account.cs:208-238`). Seeder assigns `IsSystem=true` for all template accounts.

**Update** — Only `Name/NameAr/Description` and flags are mutable. `AccountCode`/`AccountType` immutable (`private set`). No public `Update` method exists in the entity; consumers set properties directly. ❌ No canonical update API.

**Delete** — ❌ Not implemented (no method, no controller action, no soft-delete).

**Move (re-parent)** — ❌ Not implemented for canonical `Account`. `Level` is computed only as 1-or-2 at seed time (`Account.cs:234`, `TenantAccountSeeder.cs:118`); deeper hierarchy levels (3+) are **never computed** — `Level` is binary. Re-parenting at runtime is unsupported.

**Merge** — ❌ Not implemented.

**Search** — Canonical accounts are read via `AccountResolver` (`GetByCodeAsync`, `GetByCodesAsync`, `GetByCodeOrDefaultAsync`) and via reports; controllers expose no list/search endpoint for `LedgerAccounts`. (Legacy `FinancialAccountsController.GetAccounts` lists `FinancialAccounts`, not `LedgerAccounts`.)

**Validation (at entity + engine level):**
- Entity invariants (`Account.cs:11-17`): unique code/tenant, immutable code+type, balance = sum of entries, system accounts protected, no hierarchy cycles.
- Engine validation (`FinancialPostingService.ValidateJournalAsync`, `:367-481`): ≥2 lines, exactly one side >0 per line, positive amounts, debits==credits, accounts exist & active, required fields.
- `ValidateNoNegativeBalances` (`:566-612`) projects balance and throws `InsufficientFundsException` for `PreventNegative` accounts.
- Treasury authority (`ValidateTreasuryInflowAuthorityAsync` / `ValidateTreasuryOutflowAuthorityAsync`, `:614-861`) certifies cash movements against the source document (sales invoice completed+paid, order collected/settled, settlement batch, refund, payout, etc.).

**Hierarchy** — Self-referencing `ParentAccount`/`SubAccounts` (`Account.cs:79-85`), FK `DeleteBehavior.Restrict` (cannot delete a parent with children via cascade). Cycle-prevention is a stated invariant but **no runtime cycle check exists** in `Account.Create`/`TenantAccountSeeder` — enforcement relies on the seeder processing parents before children (`TenantAccountSeeder.cs:71-98`).

## 8. Financial Behavior

**Posting model** — `FinancialPostingService.PostJournalAsync` (`FinancialPostingService.cs:39-253`):
- Idempotency check before and inside the transaction (`:56-73`, `:106-121`).
- Validation, then `BeginTransactionAsync(IsolationLevel.Serializable)` (`:96-98`).
- Loads/orders accounts by Id to avoid deadlocks (`:126-145`).
- Rejects inactive accounts (`:148-152`).
- Enforces treasury inflow/outflow authority (`:154-155`).
- Enforces `PreventNegative` projected balances (`:160`).
- Generates `JE-YYYY-NNNNNN` via `JournalNumberSequence` (`:165`, `:867-894`).
- Creates `JournalEntry` + `LedgerEntry` rows, applies `ApplyEntry` to each account, persists `BalanceAfter` per line, commits (`:170-234`).
- Ledger mutation is gated by `LedgerMutationScope.Authorize()` (`:95`, `:337`).

**Opening Balance** — 🟡 Implemented only as journal postings for parties, not as a generic "set balance" API:
- `PostSupplierOpeningBalanceAsync` (`CommerceAccountingService.cs:423-496`) posts Dr/Cr between `SupplierPayables` and `OpeningBalanceEquity` (3010).
- Customer opening balances follow the same pattern (separate path; see `SUPPLIER_OPENING_BALANCE`/`PARTY_ADJUSTMENT` outbox events).
- `Account.SetOpeningBalance` exists (`Account.cs:135`) but is only a direct setter used during seeding/initialization; there is **no endpoint** exposing it.
- Seeded system accounts start at `CurrentBalance = 0` (`Account.cs:235`).

**Normal Balance** — Derived, never stored: `Asset/Expense/COGS → Debit`; `Liability/Equity/Revenue → Credit` (`AccountTypeExtensions.cs:13-25`). `Account.NormalBalance` is `[NotMapped]` (`Account.cs:68-69`).

**Debit/Credit rules** — `Account.ApplyEntry(debit, credit)`:
- Debit-normal: `CurrentBalance += debit - credit`.
- Credit-normal: `CurrentBalance += credit - debit` (`Account.cs:112-122`).
- `ReverseEntry` swaps debit/credit (`:127-130`).
- `LedgerEntry` enforces exactly one of `DebitAmount`/`CreditAmount` > 0 (`LedgerEntry.cs` invariants).

**Trial Balance** — `FinancialReportService.GetTrialBalanceAsync` (`FinancialReportService.cs:41-117`): aggregates `LedgerEntries` by account, derives `NormalBalance`, computes per-line `Balance`, exposes `IsBalanced`/`Variance`. Reports intentionally include both `Posted` and `Reversed` journals (reversals net out).

**Balance Sheet** — `GetBalanceSheetAsync` (`:277-369`): filters `Asset/Liability/Equity`, computes `TotalAssets/TotalLiabilities/TotalEquity`, `CurrentRatio`, `IsBalanced`. `IsCurrent` derived from code prefix (`IsCurrent(code)`).

**Income Statement (P&L)** — `GetProfitAndLossAsync` (`:193-271`): filters `Revenue/CostOfGoodsSold/Expense`; computes `GrossProfit`, `NetProfit`, margins.

**Cash Flow** — `GetCashFlowAsync` (`:375-454`): indirect method from P&L + AR/Inventory/AP changes; **InvestingActivities and FinancingActivities are empty lists** (`:451-452`) → 🟡 Partial.

**Retained Earnings** — ❌ **NOT IMPLEMENTED.** No `RetainedEarnings` account in `SystemAccountTemplates`; P&L `NetProfit` is not closed into any equity account; `GetBalanceSheetAsync` Equity section contains only `OpeningBalanceEquity` (3010). This is a documented gap: the system does not perform period-close / retained-earnings roll-forward.

**Clearing accounts** — `IsClearing` accounts (1110/1120/1130/1140) track money-in-transit; their balances "should trend toward zero" (`Account.cs:151-154`). `ClearingAgingReport` monitors pending settlement by age bucket (`FinancialReportService.cs:460+`). Manual clearing settlement is **disabled** (`AdminAccountingController.SettleClearing` returns `410 Gone` — must use certified settlement workflow, `:118-127`).

## 10. SQL Transactions

**Posting transaction** (`FinancialPostingService.PostJournalInternalAsync`):
- Uses EF `IExecutionStrategy` for retry (`:84-87`).
- `BeginTransactionAsync(IsolationLevel.Serializable)` (`:96-98`) — serializable to prevent race conditions.
- Accounts loaded **ordered by `Id`** to prevent deadlocks (`:126-145`).
- Idempotency re-checked inside the transaction (`:106-121`).
- Explicit `RollbackAsync` on any exception (`:244-252`).
- Balance mutation gated by `LedgerMutationScope` (`:95`).

**Business + accounting atomicity** (`AccountingTransactionBoundary`):
- `ReadCommitted` transaction wrapping a business write **and** outbox enqueue; both commit or both roll back (`:59-90`). This is how a Sale/Purchase enqueues its `AccountingOutboxMessage` in the same transaction as the business row.

**Outbox processing** (`AccountingOutboxProcessor.ProcessPendingMessagesAsync`):
- Per-message transaction; PostgreSQL `pg_advisory_xact_lock` keyed by `fnv(TenantId, BusinessEntityId)` serializes processing of the same aggregate (`:220-228`, `ComputeStableAdvisoryLockKey:380-402`).
- Claim/lease model: `TryClaim(leaseSeconds)` sets `ClaimedUntilUtc`; expired leases re-claimable (`:211-224`).
- Version ordering: earlier `AggregateVersion` messages must process first (`HasUnprocessedEarlierAggregateVersionAsync`, `:230-234,335-355`).
- Retry: exponential backoff 1/2/4/8/16 min; max 5 attempts → `IsFailed` for non-critical events (`AccountingOutboxMessage.RecordFailure`, `:229-246`).
- Critical financial-truth events use `RecordNonTerminalFinancialFailure` → **never** terminal-failed; they keep retrying while business state is committed (`:252-261`; `_criticalFinancialTruthEventTypes` set in `AccountingOutboxProcessor.cs:50-73`).
- Idempotency double-checked before posting (`ExistsByIdempotencyKeyAsync`).

**Journal numbering** — `JournalNumberSequence.AllocateNext` resets per year (`:34-45`); allocated inside the posting transaction. Note: no explicit `SELECT … FOR UPDATE` is used (the doc comment at `:865` says "SELECT FOR UPDATE" but the code uses the serializable transaction + in-tx allocation instead).

**Atomicity summary:** business write + outbox = one `ReadCommitted` tx; posting = one `Serializable` tx; outbox consumption = one tx per message with advisory lock. Rollback is explicit everywhere.

## 11. Events

**Event entity:** `AccountingOutboxMessage` (`Core/Entities/Accounting/AccountingOutboxMessage.cs`) — the transactional outbox row (tenant, event type, source type, business entity id, payload JSON, idempotency key, aggregate version, claim/retry fields).

**Producers (enqueue within business tx):** `AccountingOutboxService` (`Infrastructure/Accounting/AccountingOutboxService.cs`):
`PosSale, SaleReversal, PosPurchase, PurchaseReversal, SupplierPayment, SupplierOpeningBalance, PartyLedgerAdjustment, PosRefund, PurchaseReturn, PosExpense, ExpenseReversal, OnlinePayment, CodDelivered, WalletApproved, EcommerceRefund, UnresolvedOnlinePayment, ResolvedUnresolvedOnlinePayment, ResolvedUnresolvedCommerceHubPayment, GatewaySettlement, CodSettlement` (+ `CommerceHubLedgerPosting`).

**Consumer/processor:** `AccountingOutboxWorker` (hosted service) → `AccountingOutboxProcessor.ProcessPendingMessagesAsync` → dispatches by event type → `CommerceAccountingService.*` (maps to `PostingRequest`) → `FinancialPostingService.PostJournalAsync` → `JournalEntry` + `LedgerEntry` + `Account` balance update.

**Projection events / read-model consumers:** ❌ **NOT IMPLEMENTED for the CoA.** Financial statements are **not** event-sourced projections; `FinancialReportService` recomputes from `LedgerEntries` on every request (`FinancialReportService.cs:19`, `FinancialReportsController.GetOrCreateCachedAsync` is a no-op pass-through, `:279-287`). There is no EventStore, no projection rebuild, no materialized statement table. The outbox is the *posting* event bus, not a *projection* bus.

**Second ledger (CommerceHub):** `CommerceHubFinancialLedgerService.RecordTransactionAsync` writes `CommerceHubFinancialTransaction` rows into a **separate** store (`CommerceHubFinancialLedgerService.cs:114-159`). These are recorded (not posted to tenant `LedgerAccounts`) and later reconciled/enqueued as `CommerceHubLedgerPosting` → posted to platform/vendor ledger accounts (e.g. `MarketplaceVendorReceivable` 1420, `MarketplaceVendorPayable` 2040). This is a **distinct financial ledger** from the tenant General Ledger and must not be confused with the POS-Admin Chart of Accounts.

## 12. Runtime Architecture (implemented flow)

```
Business operation (Sale / Purchase / Refund / Settlement / Expense / SupplierPayment / OpeningBalance)
   │
   ├─ writes business row  ─┐
   │                       ├─ SAME ReadCommitted transaction (AccountingTransactionBoundary)
   └─ enqueues AccountingOutboxMessage ─┘
                              │
                  (background) AccountingOutboxWorker
                              │  pg_advisory_xact_lock(tenant, entity); claim/lease; version order
                              ▼
                  AccountingOutboxProcessor → CommerceAccountingService
                              │  builds PostingRequest (Dr/Cr lines, idempotency key)
                              ▼
                  FinancialPostingService.PostJournalAsync
                              │  Serializable tx; idempotency recheck; load accounts ordered by Id;
                              │  treasury authority + PreventNegative checks; allocate JE number
                              ▼
                  JournalEntry + LedgerEntry rows  ──►  Account.ApplyEntry updates CurrentBalance
                              │
                              ▼
                  Reports (on demand): TrialBalance / P&L / BalanceSheet / CashFlow / ClearingAging
                              │  recomputed from LedgerEntries every request (no projection store)
```

Treasury operations (`TreasuryTransferService.TransferAsync/SettleClearingAsync/DepositToBankAsync`) are a direct (non-outbox) path that also builds a `PostingRequest` and calls the posting engine; they require active same-tenant treasury authority (`RequireTreasuryTypeAsync`, `TreasuryTransferService.cs:202-229`).

**POS-Admin Chart-of-Accounts specific UI:** ❌ none. The flow above is fully backend. The only CoA-related HTTP surface is `POST /api/admin/accounting/seed` (admin) and the read-only `FinancialReportsController` endpoints. The legacy `FinancialAccountsController` CRUD surface targets the **shadow** `FinancialAccounts` table, not `LedgerAccounts`.

## 13. Browser Test Specification

> Because the canonical Chart of Accounts has **no POS-Admin UI and no CRUD API**, browser testing is necessarily limited to (a) the admin seed endpoint, (b) the financial-reports read endpoints, and (c) guard/negative cases reachable via API. Where a CoA management UI is expected, mark it as **NOT IMPLEMENTED — no surface to test**.

**Preconditions:** tenant exists; `X-Tenant-Id` header set; `Admin` role for seed endpoint.

### 13.1 Seeding (admin)
- `POST /api/admin/accounting/seed` → 200, body `{message:"Chart of accounts seeded successfully", tenantId}`.
- **Idempotency:** call twice → second call reports "already have accounts" (no duplicate codes). Assert `LedgerAccounts` count by tenant is stable and `IX_LedgerAcct_TenantCode` is not violated.
- **Hierarchy:** assert seeded `Cashbox Main` (1010) has `ParentAccountId` = `Cash and Bank` (1000); `Visa Clearing` (1110) parent = `Clearing Accounts` (1100).
- **System flags:** assert `IsSystem=true` for all template accounts; `PreventNegative=true` for 1010/1030/1040/2105/2040; `IsClearing=true` for 1110/1120/1130/1140.

### 13.2 Financial reports (read)
- `GET /api/financialreports/trial-balance?from=&to=` → `IsBalanced == true` (variance 0) for any posted period.
- `GET /api/financialreports/balance-sheet?asOf=` → `TotalAssets == TotalLiabilities + TotalEquity`; `IsBalanced == true`.
- `GET /api/financialreports/profit-loss?from=&to=` → `GrossProfit == Revenue - COGS`; `NetProfit == GrossProfit - Expenses`.
- `GET /api/financialreports/clearing-aging` → clearing accounts listed with age buckets; `TotalPending` matches sum of `IsClearing` account balances.
- `GET /api/financialreports/dashboard` → cached 30s; metrics consistent with P&L + BalanceSheet + ClearingAging.

### 13.3 Failure / business-validation cases (API-level)
- **Post to inactive account:** deactivate an account (direct DB), attempt a posting that hits it → expect `InactiveAccountException` (400/500 depending on caller). No CoA UI toggle exists to deactivate, so this is verified at the engine/integration-test level, not browser.
- **Negative balance on `PreventNegative` account:** attempt treasury outflow exceeding cashbox balance → `InsufficientFundsException`.
- **Manual clearing settlement:** `POST /api/admin/accounting/treasury/settle` → **410 Gone** (`SETTLEMENT_AUTHORITY_REQUIRED`). Assert it is rejected.
- **Unbalanced journal:** the engine rejects `dr != cr` with `UnbalancedJournalException` — exercised via integration tests (`FinancialPostingServiceTests.cs`), not browser.
- **Cross-tenant:** a request with Tenant A's `X-Tenant-Id` must never return/read Tenant B's `LedgerAccounts` (enforced by `TenantId` filter + unique index).

### 13.4 What cannot be browser-tested (gaps)
- Create/edit/delete/re-parent a `LedgerAccounts` account — **no endpoint/UI**.
- Toggle `IsActive` on a canonical account — **no endpoint/UI**.
- Set opening balance via UI — only via party-opening-balance journal postings.

## 16. Documentation Validation (myth vs implementation)

- ❌ Myth: "The Account stores the authoritative current balance."
  ✅ `Account.CurrentBalance` is a **denormalized cache**; the invariant states it must equal the sum of ledger entries (`Account.cs:14`). Truth = `LedgerEntries`.

- ❌ Myth: "Parent/control accounts receive manual postings."
  ✅ Any active account can be posted to via journal lines; there is no "control vs posting" flag. Posting is by `AccountId` on `LedgerEntry` (`LedgerEntry.cs:35-36`), not by account level.

- ❌ Myth: "The Chart of Accounts owns accounting transactions."
  ✅ The **Ledger** (`JournalEntry`/`LedgerEntry`) owns transactions. `Account` only references them (`Account.cs` has no journal collection).

- ❌ Myth: "Accounts can be freely created/edited/deleted from POS Admin."
  ✅ Canonical `LedgerAccounts` has **no CRUD API and no UI**. Creation is seed-only; code/type immutable; deletion absent. (The `FinancialAccountsController` CRUD targets the **legacy** `FinancialAccounts` table, not the ledger.)

- ❌ Myth: "There is a Retained Earnings account and period close."
  ✅ ❌ NOT IMPLEMENTED. Equity contains only `OpeningBalanceEquity` (3010); P&L net profit is never closed.

- ❌ Myth: "Financial statements are pre-computed projections."
  ✅ Reports are **recomputed from `LedgerEntries` every request** (`FinancialReportService`); no projection store exists.

- ❌ Myth: "Opening balance is a simple field you set on an account."
  ✅ Implemented only as **journal postings** to `SupplierPayables`/`OpeningBalanceEquity` (and customer equivalent); `SetOpeningBalance` is a direct setter with no endpoint.

- ❌ Myth: "`Level` encodes full tree depth."
  ✅ `Level` is binary (1 = top, 2 = has-parent); deeper hierarchy is not tracked (`Account.cs:234`; `TenantAccountSeeder.cs:118`).

- ❌ Myth: "CommerceHub financials post directly into the tenant ledger."
  ✅ CommerceHub writes its **own** `CommerceHubFinancialTransaction` store, then reconciles/enqueues `CommerceHubLedgerPosting` to post to platform/vendor ledger accounts — a separate path, not a direct CoA mutation.

- ⚠️ Myth: "`FinancialAccount` and `Account` are the same thing."
  ✅ They are **two different models/tables**. `Account`→`LedgerAccounts` is authoritative for the ledger; `FinancialAccount`→`FinancialAccounts` is a legacy shadow with its own `AccountNumber` and soft-delete.

## 17. Final Architecture Conclusion

**Account Authority.** The Chart of Accounts is a per-tenant set of immutable-identity `Account` nodes (table `LedgerAccounts`), seeded from `SystemAccountTemplates` and protected by a unique `(TenantId, AccountCode)` index and `xmin` optimistic concurrency. `AccountCode` and `AccountType` are immutable; `Name`/flags are mutable; **deletion and re-parenting are not implemented**.

**Financial Authority.** The **General Ledger** (`JournalEntry` + `LedgerEntry`) is the single source of financial truth. `Account.CurrentBalance` is a denormalized projection maintained exclusively by `FinancialPostingService` inside a `Serializable` transaction. All cash movement requires certified-source treasury authority; `PreventNegative` accounts are balance-checked pre-commit.

**Runtime Flow.** Business op → outbox message (same `ReadCommitted` tx) → `AccountingOutboxWorker`/`Processor` (advisory-locked, version-ordered, idempotent) → `CommerceAccountingService` → `FinancialPostingService` (Serializable, balanced, authorized) → `JournalEntry`/`LedgerEntry` + balance update → reports recomputed on demand.

**Aggregate Ownership.** `Account` owns identity/hierarchy/flags/denormalized balance. `Journal` owns immutability/reversal. `Ledger` owns balances/truth. `TreasuryTransferService` owns transfer/deposit/settle orchestration. `FinancialReportService` owns read-model derivation. `TenantAccountSeeder` owns seeding.

**Transaction Model.** Two transaction scopes: business+outbox in `ReadCommitted` (`AccountingTransactionBoundary`); posting in `Serializable` with accounts ordered by Id (deadlock avoidance) and idempotency re-checked inside the tx. Outbox consumption uses `pg_advisory_xact_lock(tenant, entity)` + claim/lease + exponential backoff; critical financial events never reach a terminal failed state.

**Projection Strategy.** ❌ There is **no event-sourced projection / materialized statement store** for the Chart of Accounts. Financial statements are pure functions over `LedgerEntries`, recomputed per request. The outbox is the *posting* event bus, not a *projection* bus. The CommerceHub domain maintains a **separate** financial transaction ledger that is reconciled into the tenant ledger via the `CommerceHubLedgerPosting` event.

**Gaps (explicitly NOT IMPLEMENTED):**
1. No CRUD API / POS-Admin UI for canonical `LedgerAccounts` (create/edit/delete/re-parent/toggle-active).
2. No Retained Earnings account / period-close / net-profit roll-forward.
3. `Level` tracks only depth 1–2; no deep-hierarchy support or cycle detection at runtime.
4. No soft-delete/archive state for canonical accounts.
5. Cash Flow `InvestingActivities`/`FinancingActivities` are empty.
6. Legacy `FinancialAccount`/`FinancialTransactions` shadow model coexists with the authoritative ledger and should be treated as deprecated to avoid dual-source-of-truth confusion.
