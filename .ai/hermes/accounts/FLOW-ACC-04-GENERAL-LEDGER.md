## 0. Critical Orientation: Two "Ledgers" Exist — Only One Is the GL

This is the single most important architectural fact and prevents conflating two distinct systems:

**A. General Ledger (AUTHORITATIVE FINANCIAL TRUTH)** — the subject of this document
- Entities: `JournalEntry` (table `LedgerJournalEntries`) + `LedgerEntry` (table `LedgerLines`), referencing `Account` (table `LedgerAccounts`).
- Double-entry, immutable, per-tenant. The financial source of truth.
- Written **only** by `FinancialPostingService` (`PostJournalAsync` / `ReverseJournalAsync`) inside a `Serializable` transaction, gated by `LedgerMutationScope`.
- Read by `FinancialReportService` (Trial Balance, General Ledger, P&L, Balance Sheet, Cash Flow, Clearing Aging) — each recomputed from `LedgerEntries` on every request.

**B. Party Sub-Ledger (SHADOW / SEPARATE)** — `LedgerService` / `ILedgerService` (`PointOfSale.API/Services/LedgerService.cs`)
- Operates on `AccountLedger` rows (table `AccountLedgers`), plus `CustomerTransactions` / `SupplierTransactions`, and maintains a `Customer.Balance` / `Supplier.Balance` scalar.
- This is a **party/AR-AP running-balance ledger**, NOT the GL. It is a different aggregate, different table, different balance semantics (`RunningBalance = prior + debit − credit` regardless of account type — `LedgerService.cs:218,385`).
- It is explicitly called out throughout so the GL is not confused with it. **It is not the financial source of truth for the GL.**

> Status legend used throughout: ✅ Implemented · 🟡 Partially Implemented · ❌ NOT IMPLEMENTED.

## 1. Executive Summary

**What is the General Ledger?**
A per-tenant, immutable, double-entry record of every financial transaction. It is composed of `JournalEntry` header rows (`LedgerJournalEntries`) and `LedgerEntry` line rows (`LedgerLines`). Each journal is balanced (Σ debits == Σ credits) and carries at least two lines. Each `LedgerEntry` records one account being debited or credited, plus the account's `BalanceAfter` (the running balance immediately after that line). See `JournalEntry.cs:8-17` (invariants) and `LedgerEntry.cs:7-15` (invariants).

**Who owns it?**
The General Ledger is owned by the **posting engine** — `FinancialPostingService` — and the data it writes. No UI, no controller, and no other service may mutate a `JournalEntry` or `LedgerEntry` once posted. Mutation is gated by `LedgerMutationScope.Authorize()` (`LedgerMutationScope.cs:14`), which only `FinancialPostingService` invokes (`FinancialPostingService.cs:95,337`).

**What does it own?**
- The authoritative record of every accounting journal (`LedgerJournalEntries`).
- The authoritative debit/credit lines and per-line running balances (`LedgerLines.BalanceAfter`).
- The audit trail of postings and reversals (`JournalStatus`, `ReversedByJournalId`, `ReversesJournalId`, `ReversalReason`).
- The basis from which all financial statements are derived.

**What does it NOT own?**
- It does **not** own account identity/structure — that is `Account` (Chart of Accounts). The GL references `AccountId` (`LedgerEntry.cs:35-36`) but does not own the account.
- It does **not** own Treasury, Chart of Accounts, or the Posting Engine (the engine owns the *act of posting*; the GL owns the *recorded result*).
- It does **not** own `Account.CurrentBalance` as truth — that is a denormalized cache; the truth is `Σ LedgerEntries` (`Account.cs:14`, `FinancialReportService.cs:19` "Ledger is the ONLY source of truth").
- It does **not** own the party sub-ledger (`AccountLedger` / `CustomerTransactions`) — that is a separate system (§0-B).
- It does **not** own reporting/statements — those are derived read models (`FinancialReportService`).

**What is the financial source of truth?**
The General Ledger (`LedgerJournalEntries` + `LedgerLines`) in PostgreSQL, per tenant. `Account.CurrentBalance` is a derived cache kept in sync by the posting engine. Reports read exclusively from `LedgerEntries` (`FinancialReportService.cs:16-22`, implements `ILedgerOnlyService` so CI/CD fails on any business-table read).

## 4. Ledger Ownership

**Belongs to the General Ledger (written only by the posting engine within a `LedgerMutationScope`):**

- **Journal headers** — created by `JournalEntry.Create(...)` (`JournalEntry.cs:180-217`), only inside `FinancialPostingService.PostJournalInternalAsync` (`FinancialPostingService.cs:170-186`).
- **Journal lines** — created by `LedgerEntry.CreateDebit`/`CreateCredit` (`LedgerEntry.cs:111-170`), only inside the posting engine (`FinancialPostingService.cs:201-224`).
- **Per-line `BalanceAfter`** — set to `Account.CurrentBalance` *after* `Account.ApplyEntry` is called for that line (`FinancialPostingService.cs:197-222`). The GL owns this running-balance audit column.
- **Reversal linkage** — `MarkReversed` / `MarkAsReversal` set the reversal FKs and reason (`JournalEntry.cs:119-135`); invoked only by `ReverseJournalInternalAsync` (`FinancialPostingService.cs:338-351`).
- **Idempotency binding** — a journal is permanently bound to its `IdempotencyKey` (unique per tenant); the key may not be reassigned to a different posting (`EnsureIdempotentRequestMatches`, `FinancialPostingService.cs:526-559`).

**Does NOT belong to the GL (owned by other aggregates/services):**

- Account identity / hierarchy / flags → `Account` aggregate (Chart of Accounts, `FLOW-ACC-01`).
- Account denormalized `CurrentBalance` → owned by `Account`, **mutated only** by the posting engine via `ApplyEntry`/`ReverseEntry` (`Account.cs:112-130`), gated by `LedgerMutationScope`.
- Posting logic / treasury authority / validation → `FinancialPostingService` (`ValidateTreasuryInflowAuthorityAsync`/`ValidateTreasuryOutflowAuthorityAsync`, `:614-861`).
- Reports / statements → `FinancialReportService` (read models over `LedgerEntries`).
- Event transport → `AccountingOutboxMessage` + Processor/Worker.
- Party AR/AP sub-ledger → `LedgerService` (`AccountLedger` etc.), a separate aggregate.

## 5. Journal Lifecycle

Implemented stages (from `JournalEntry.cs`, `FinancialPostingService.cs`, `JournalStatus.cs`):

1. **Create (Post)** — `PostJournalAsync` → `PostJournalInternalAsync` (`FinancialPostingService.cs:39-253`). Validates, begins `Serializable` tx, allocates journal number, creates `JournalEntry` (status `Posted`) + `LedgerEntries`, applies balances, commits. Idempotency-checked before and inside the tx.
2. **Validate** — `ValidateJournalAsync` (`FinancialPostingService.cs:367-481`): ≥2 lines, one side >0 per line, positive amounts, debits==credits, accounts exist & active, required fields, idempotency key present. Also treasury authority + `PreventNegative` projected-balance checks at post time (`:154-160,566-612`).
3. **Post** — equivalent to Create above; status is `Posted` on creation (`JournalEntry.cs:215`). A posted journal affects balances.
4. **Read** — `GetJournalAsync` (by id), `GetJournalByIdempotencyKeyAsync`, `ExistsByIdempotencyKeyAsync` (`IFinancialPostingService.cs:63-84`); and reports (`FinancialReportService`).
5. **Reverse** — `ReverseJournalAsync` (`FinancialPostingService.cs:256-359`): loads original, builds a new journal with swapped debits/credits, posts it (status `Posted`, `SourceType="Reversal"`), then `original.MarkReversed(reversalJournal.Id, reason)` flips the original to `Reversed`. Idempotency key `REVERSE:{tenantId}:{journalId}` (`FinancialPostingService.cs:287`). Reversal is the **only** mutation of an existing journal.
6. **Archive** — ❌ NOT IMPLEMENTED. No archive state on `JournalEntry`/`JournalStatus`.
7. **Delete** — ❌ NOT IMPLEMENTED. No delete method, no endpoint. `LedgerEntry` cascade-deletes only if its parent `JournalEntry` is deleted — but nothing deletes a journal (and the engine never does).
8. **Cancel** — ❌ NOT IMPLEMENTED. No `Cancelled` status (enum has only `Posted`/`Reversed`).
9. **Restore** — ❌ NOT IMPLEMENTED. A `Reversed` journal cannot be "restored"; a new forward journal would be required. Re-reversing is blocked (`JournalAlreadyReversedException`, `FinancialPostingService.cs:275-276`).

**State machine (the only legal transition):** `Posted → Reversed`. `Reversed` is terminal for that journal header (it stays for audit; its effects are negated by the reversal journal).

## 6. Aggregate Analysis

```
Tenant
 └── General Ledger (logical — the set of JournalEntry + LedgerEntry rows)
      ├── JournalEntry aggregate          (header; immutable; status Posted/Reversed)
      │    └── LedgerEntry (lines)         (cascade; one debit/credit each; BalanceAfter)
      │         └── references AccountId   (cross-aggregate reference, Restrict, NOT ownership)
      ├── JournalNumberSequence aggregate (one per tenant; JE numbering, resets per year)
      └── AccountingOutboxMessage         (event that triggers a posting)

Account aggregate (Chart of Accounts; separate — see FLOW-ACC-01)
      └── referenced by LedgerEntry.AccountId (the ledger reads the account, does not own it)

Read models (NOT aggregates, NOT persisted):
      └── TrialBalance / GeneralLedger / P&L / BalanceSheet / CashFlow / ClearingAging
           (recomputed from LedgerEntries every request — FinancialReportService)

Separate: Party Sub-Ledger (LedgerService → AccountLedger / CustomerTransactions / SupplierTransactions)
Separate: CommerceHub financial store (CommerceHubFinancialTransaction → reconciled into tenant GL)
```

**Ownership:**
- **Journal header + lines + reversal linkage + idempotency binding** → General Ledger (written exclusively by `FinancialPostingService`).
- **Account identity / hierarchy / flags / denormalized balance** → `Account` (Chart of Accounts).
- **The act of posting (validation, treasury authority, balance math, numbering, tx)** → `FinancialPostingService`.
- **JE numbering** → `JournalNumberSequence` (owned/allocated by the posting engine inside the tx).
- **Reading / statements** → `FinancialReportService` (derived).
- **Event transport** → `AccountingOutboxMessage` + Processor/Worker.

The General Ledger owns the *recorded financial truth*; the posting engine owns the *process that writes it*; the Chart of Accounts owns *account structure*; reports own *derivation*.

## 7. Ledger Behavior

**Posting** — `PostJournalAsync` (`FinancialPostingService.cs:39-253`):
1. Idempotency check (before tx, `IgnoreQueryFilters` because outbox worker may lack tenant context) — return existing if key matches (`:56-73`).
2. `ValidateJournalAsync` (`:78`).
3. Begin `Serializable` tx if not already in one; wrap in `IExecutionStrategy` for retry (`:83-88`).
4. Re-check idempotency inside tx (race guard, `:106-121`).
5. Load/order accounts by `Id` (deadlock avoidance), reject inactive (`:126-152`).
6. Treasury inflow + outflow authority checks (`:154-155`).
7. `ValidateNoNegativeBalances` projected check (`:160`).
8. `GenerateJournalNumberAsync` (`:165`).
9. `JournalEntry.Create` + `LedgerEntry.Create{Debit|Credit}` per line, applying `Account.ApplyEntry` and capturing `BalanceAfter = account.CurrentBalance` (`:170-225`).
10. `SaveChangesAsync` + commit; explicit `RollbackAsync` on exception (`:230-252`).

**Validation** — see §5 step 2 and §9. Enforced both pre-tx (`ValidateJournalAsync`) and at apply time (`PreventNegative`, treasury authority). DB-level enforcement: unique indexes on `(TenantId, IdempotencyKey)` and `(TenantId, JournalNumber)` (`JournalEntryConfiguration.cs:19-26`), and check constraints `CK_LedgerLines_SingleSide` / `CK_LedgerLines_PositiveAmounts` (`LedgerEntryConfiguration.cs:54-61`).

**Reading** — `GetJournalAsync` / `GetJournalByIdempotencyKeyAsync` (`FinancialPostingService.cs:484-507`); reports in `FinancialReportService`. Reads use `AsNoTracking()` and a `RepeatableRead` consistent-read transaction (`BeginConsistentReadTransactionAsync`, `FinancialReportService.cs:650-658`).

**Searching / Filtering / Paging** — ❌ NOT IMPLEMENTED at the HTTP/API level. There is **no journal list/search/filter/paging endpoint** (search for `journal` GET routes in `Controllers` returned none; `IFinancialPostingService` exposes only get-by-id, get-by-idempotency-key, exists-by-key). The only GL query surface is per-account General Ledger and the aggregate report endpoints (§12). Internally, `SalesController.cs:1792-1802` filters `JournalEntries` by `(TenantId, SourceId, Status, SourceType)` for reversal, but this is not a general query API.

**History** — per-account history is `GetGeneralLedgerAsync` (chronological `GeneralLedgerEntry` rows with `BalanceAfter`, `FinancialReportService.cs:123-187`). Full audit history is the immutable `LedgerJournalEntries` + `LedgerLines` themselves; nothing is deleted.

**Reversal** — `ReverseJournalAsync` (`FinancialPostingService.cs:256-359`): builds swapped-line `PostingRequest`, posts it as a new `Posted` journal with `SourceType="Reversal"` and `IdempotencyKey="REVERSE:{tenant}:{journalId}"`, then marks the original `Reversed`. Invoked by: (a) `SalesController` sale-update path (`SalesController.cs:1806-1811`), and (b) the outbox processor for refunds/returns (`AccountingOutboxProcessor.cs:1449,1620,2225`). Reversal is the only way to "undo" a journal.

**Delete** — ❌ NOT IMPLEMENTED for journals. Controllers that delete business documents (Sale/Purchase) explicitly forbid deletion if posted journals exist — instead they require reversal (`SalesController.cs:1745-1748`, `PurchasesController.cs:1339-1342`).

## 8. Financial Behavior

**Double Entry** — every journal must have Σ debits == Σ credits (`JournalEntry.IsBalanced`, `:171`; enforced `UnbalancedJournalException`, `FinancialPostingService.cs:437-441`). Each line is exactly one debit XOR one credit (`LedgerEntry` invariants; DB check `CK_LedgerLines_SingleSide`).

**Debit / Credit** — `LedgerEntry.CreateDebit`/`CreateCredit` (`LedgerEntry.cs:111-170`). `Account.ApplyEntry(debit, credit)` updates `CurrentBalance` by normal balance: Debit-normal → `+= debit − credit`; Credit-normal → `+= credit − debit` (`Account.cs:112-122`). `ReverseEntry` swaps the operands (`Account.cs:127-130`).

**Balanced Journals** — enforced at validation (≥2 lines, one side per line, positive, balanced). `JournalEntry.TotalDebits`/`TotalCredits`/`IsBalanced` are computed from `LedgerEntries` (`:158-171`).

**Current Balance** — `Account.CurrentBalance` is a **denormalized cache**; the invariant states it must equal Σ ledger entries (`Account.cs:14`). It is maintained *only* by `ApplyEntry`/`ReverseEntry`, called by the posting engine inside the tx. Reports do **not** trust it for truth — they recompute from `LedgerEntries` (e.g. `GetAccountBalanceAsOfAsync`, `FinancialReportService.cs:601-635`).

**Balance After** — `LedgerEntry.BalanceAfter` is the account's `CurrentBalance` captured right after that line's `ApplyEntry` (`FinancialPostingService.cs:197-222`). It provides a point-in-time running balance and an audit trail. `GeneralLedgerReport` exposes it per entry (`GeneralLedgerReport.cs:54`).

**PreventNegative** — for accounts flagged `PreventNegative` (cashbox/bank), `ValidateNoNegativeBalances` projects the post-apply balance using normal balance and throws `InsufficientFundsException` if < 0 (`FinancialPostingService.cs:566-612`). Enforced pre-commit.

**Immutable Journals** — immutable by design: no update/delete methods; `Status` only `Posted→Reversed`; `LedgerMutationScope` gates any balance/reversal persistence to the posting engine (`LedgerMutationScope.cs`).

**Financial Authority** — the GL is the financial source of truth; the posting engine is its sole writer and enforces treasury inflow/outflow authority against certified source documents (sales invoices completed+paid, orders collected/settled, settlement batches, refunds, payouts, etc. — `FinancialPostingService.cs:614-861`). Cash movements are capped to the authoritative source amount (`previouslyPosted + net <= authorized`, `:717,856`).

**Ledger Integrity** — guaranteed by: (a) immutable journals, (b) unique `(TenantId, IdempotencyKey)` + `(TenantId, JournalNumber)` indexes, (c) DB check constraints on `LedgerLines`, (d) `Serializable` posting tx with accounts locked/ordered by Id, (e) `LedgerMutationScope`, (f) idempotency re-check inside tx, (g) reports that recompute from `LedgerEntries` (a corruption of `CurrentBalance` does not affect reports).

**Audit Trail** — every journal carries `PostedAtUtc`, `SourceType`, `SourceId`, `SourceReference`, `Description`, `CreatedByUserId`, `IdempotencyKey`, `Status`, and reversal metadata (`ReversedByJournalId`, `ReversesJournalId`, `ReversalReason`). `LedgerEntry` carries `LineNumber`, `LineDescription`, `CreatedAtUtc`, `BalanceAfter`. Nothing is overwritten or deleted.

**Reversal** — see §5/§7. Reversal creates a new balanced journal that negates the original; both remain for audit. The original is marked `Reversed` and cannot be reversed twice (`JournalAlreadyReversedException`).

## 10. SQL Transactions

**Posting transaction** (`PostJournalInternalAsync`, `FinancialPostingService.cs:90-253`):
- `IExecutionStrategy` (retry on transient failures) when the service owns the tx (`:84-87`).
- `BeginTransactionAsync(IsolationLevel.Serializable)` (`:96-98`) — serializable to prevent race conditions on numbering/balances.
- Accounts loaded **ordered by `Id`** to prevent deadlocks (`:126-145`).
- Idempotency re-checked **inside** the transaction (`:106-121`).
- Explicit `RollbackAsync` on any exception (`:244-252`).
- Balance mutation gated by `LedgerMutationScope` (`:95`).

**Reversal transaction** (`ReverseJournalAsync`, `:256-328`):
- Separate `Serializable` tx; posts the reversal journal then `MarkReversed` the original; explicit rollback on failure (`:303-321`).

**Consistent read transaction** (`FinancialReportService.BeginConsistentReadTransactionAsync`, `:650-658`):
- `IsolationLevel.RepeatableRead` for report reads (snapshot consistency within the report).

**Journal numbering** — `JournalNumberSequence` is one row per tenant (PK `TenantId`), `CurrentYear` + `NextNumber`, `AllocateNext(year)` resets per year and returns `JE-{year}-{NextNumber:D6}` (`JournalNumberSequence.cs:34-45`). Allocated **inside** the posting tx (`GenerateJournalNumberAsync`, `FinancialPostingService.cs:867-894`). Note: the doc comment at `:865` says "SELECT FOR UPDATE" but the code uses the serializable transaction + in-tx allocation (no explicit `SELECT … FOR UPDATE`).

**Atomicity summary:** outbox-enqueue + business write = one `ReadCommitted` tx (elsewhere, `AccountingTransactionBoundary`); posting = one `Serializable` tx; reversal = one `Serializable` tx; report read = one `RepeatableRead` tx. Rollback is explicit everywhere; no implicit partial commits.

**Concurrency / deadlock prevention:** accounts locked & ordered by `Id`; serializable isolation; execution-strategy retry; advisory locks at the outbox-processing layer (see §11).

## 11. Events

**Event entity:** `AccountingOutboxMessage` — the transactional outbox row (tenant, event type, source type, business entity id, payload JSON, idempotency key, aggregate version, claim/retry fields). It is the **posting event bus**, not a projection bus.

**Producers:** `AccountingOutboxService` enqueues within the business `ReadCommitted` transaction (sale/purchase/refund/settlement/expense/supplier-payment/opening-balance, etc. — see `FLOW-ACC-01` §11).

**Consumer/processor:** `AccountingOutboxWorker` (hosted service) → `AccountingOutboxProcessor.ProcessPendingMessagesAsync` → dispatches by event type → `CommerceAccountingService` (maps to `PostingRequest`) → `IFinancialPostingService.PostJournalAsync` (or `ReverseJournalAsync` for refunds/returns: `AccountingOutboxProcessor.cs:1449,1620,2225`).

**Outbox processing guarantees:**
- Per-message `ReadCommitted` tx; `pg_advisory_xact_lock` keyed by `fnv(TenantId, BusinessEntityId)` serializes the same aggregate (`AccountingOutboxProcessor`).
- Claim/lease model: `TryClaim(leaseSeconds)` sets `ClaimedUntilUtc`; expired leases re-claimable.
- Version ordering: earlier `AggregateVersion` messages processed first.
- Retry: exponential backoff; max attempts → `IsFailed` for non-critical events. **Critical financial-truth events never reach a terminal failed state** (`RecordNonTerminalFinancialFailure`) — they keep retrying while business state is committed.

**Projection events / read-model consumers:** ❌ **NOT IMPLEMENTED for the GL.** Financial statements are **not** event-sourced projections. `FinancialReportService` recomputes from `LedgerEntries` on every request (`FinancialReportService.cs:16-22`); `GetOrCreateCachedAsync` in `FinancialReportsController` is a **no-op pass-through** (`:279-287`, 30s memory cache only). There is no EventStore, no projection rebuild, no materialized statement table. The outbox is the *posting* event bus, not a *projection* bus.

**Second ledger (CommerceHub):** `CommerceHubFinancialTransaction` is a separate store, later reconciled/enqueued as `CommerceHubLedgerPosting` into platform/vendor GL accounts — distinct from the tenant GL (called out to avoid confusion).

## 12. Runtime Architecture (implemented flow)

```
Business operation (Sale / Purchase / Refund / Settlement / Expense / SupplierPayment / OpeningBalance)
   │
   ├─ writes business row  ─┐
   │                       ├─ SAME ReadCommitted transaction (AccountingTransactionBoundary)
   └─ enqueues AccountingOutboxMessage ─┘
                              │
                  (background) AccountingOutboxWorker
                              │  pg_advisory_xact_lock(tenant, entity); claim/lease; version order
                              ▼
                  AccountingOutboxProcessor → CommerceAccountingService
                              │  builds PostingRequest (balanced Dr/Cr lines, idempotency key)
                              ▼
                  FinancialPostingService.PostJournalAsync
                              │  Serializable tx; LedgerMutationScope.Authorize();
                              │  idempotency recheck; load accounts ordered by Id;
                              │  treasury authority + PreventNegative checks; allocate JE number
                              ▼
                  JournalEntry (LedgerJournalEntries, status Posted)
                      + LedgerEntries (LedgerLines, one Dr/XOR Cr each, BalanceAfter)
                              │
                              ▼
                  Account.ApplyEntry updates Account.CurrentBalance (denormalized cache)
                              │
                              ▼
   Reports (on demand, RepeatableRead, recomputed every request from LedgerEntries):
       TrialBalance / GeneralLedger / P&L / BalanceSheet / CashFlow / ClearingAging
                              │
   HTTP read surface: GET api/financialreports/{trial-balance|general-ledger/{accountId}|
                                              profit-loss|balance-sheet|cash-flow|clearing-aging|accounts|dashboard}

Reversal path (only mutation of an existing journal):
   ReverseJournalAsync(tenant, journalId, reason)
       → builds swapped Dr/Cr PostingRequest (IdempotencyKey = REVERSE:{tenant}:{journalId})
       → PostJournalAsync posts a new journal (SourceType="Reversal")
       → original.MarkReversed(reversalJournalId, reason)   // Posted → Reversed
```

## 13. Browser Test Specification

> The GL has **no create/edit/delete UI** and **no journal-list UI**. The only browser-reachable surface is the read-only `FinancialReportsController` endpoints (requires `Authorization` + `X-Tenant-Id`). Treasury/posting flows are backend/outbox-driven. Where a GL management UI is expected, mark it **NOT IMPLEMENTED — no surface to test**.

**Preconditions:** tenant exists; `X-Tenant-Id` header set; `Authorize` (JWT) present.

### 13.1 General Ledger report (read)
- `GET /api/financialreports/general-ledger/{accountId}?from=…&to=…` → 200 with `GeneralLedgerReport`.
  - Assert `OpeningBalance` equals the account balance as of `from − 1 day` (recomputed from `LedgerEntries`).
  - Assert each `Entries[i].BalanceAfter` equals the running balance after applying that line in `JournalDate, LineNumber` order.
  - Assert `ClosingBalance == OpeningBalance + Σ(Debit − Credit)` over the period.
  - Assert every entry's `JournalNumber` is unique and well-formed `JE-YYYY-NNNNNN`.
  - Assert `TotalDebits`/`TotalCredits` equal the sum of entry debits/credits.
- **Empty period / no entries:** `Entries` is empty, `OpeningBalance == ClosingBalance`.

### 13.2 Trial balance / statements (read)
- `GET /api/financialreports/trial-balance?from=&to=` → `IsBalanced == true` (variance 0) for any posted period.
- `GET /api/financialreports/balance-sheet?asOf=` → `TotalAssets == TotalLiabilities + TotalEquity`; `IsBalanced == true`.
- `GET /api/financialreports/profit-loss?from=&to=` → `GrossProfit == Revenue − COGS`; `NetProfit == GrossProfit − Expenses`.
- `GET /api/financialreports/clearing-aging?asOf=` → clearing accounts listed with age buckets; `TotalPending` matches Σ `IsClearing` account balances.
- `GET /api/financialreports/dashboard` → metrics consistent with P&L + BalanceSheet + ClearingAging; 30s cache.

### 13.3 Ledger integrity & reversal verification
- **Reversal (via sale-update or outbox refund/return):** after a reversal, assert the original journal `Status == Reversed` and `ReversedByJournalId` points to the new reversal journal; assert the reversal journal has `SourceType == "Reversal"` and swapped debits/credits; assert `TrialBalance.IsBalanced == true` still (reversals net out).
- **Idempotency:** triggering the same posting twice (same idempotency key) returns the *same* `JournalNumber` (no duplicate). Hard to exercise from browser; verified at integration level (`FinancialPostingServiceTests.PostJournalAsync_DuplicateIdempotencyKey_ReturnsSameJournal`).
- **Immutability:** there is **no** endpoint to edit/delete a journal — assert 404/405 for any PUT/DELETE on a journal route.

### 13.4 Failure / business-validation cases (API/integration level — not browser)
- **Unbalanced journal:** engine rejects `dr != cr` with `UnbalancedJournalException` (integration test `FinancialPostingServiceTests.PostJournalAsync_UnbalancedJournal_ThrowsUnbalancedJournalException`).
- **Single-line journal:** rejected (`InvalidJournalException`, rule 1).
- **Both debit & credit on one line:** rejected (rule 2; also DB check `CK_LedgerLines_SingleSide`).
- **Negative amount:** rejected (rule 3; DB check `CK_LedgerLines_PositiveAmounts`).
- **Inactive account:** rejected (`InactiveAccountException`).
- **PreventNegative breach:** treasury outflow exceeding cashbox balance → `InsufficientFundsException`.
- **Double reversal:** `JournalAlreadyReversedException`.
- **Cross-tenant:** a request with Tenant A's `X-Tenant-Id` must never return/read Tenant B's `LedgerJournalEntries`/`LedgerLines` (enforced by `TenantId` filter + unique indexes).

### 13.5 What cannot be browser-tested (gaps)
- Create/edit/delete/archive a journal — **no endpoint/UI**.
- List/search/filter/paging journals — **no endpoint/UI**.
- Manual journal entry form — **not implemented** (posting is outbox/treasury/internal only).
- Set `Account.CurrentBalance` directly — only via posting engine.

## 16. Documentation Validation (myth vs implementation)

- ❌ Myth: "The General Ledger can be edited after posting."
  ✅ Journals are immutable. Only transition is `Posted → Reversed`; no update/delete methods exist (`JournalEntry.cs:11-16,250-287`).

- ❌ Myth: "There is a journal list/search/filter/paging UI."
  ✅ ❌ NOT IMPLEMENTED. No controller action; `IFinancialPostingService` exposes only get-by-id / get-by-idempotency-key / exists (`IFinancialPostingService.cs:60-84`). Only the per-account General Ledger report and aggregate reports are queryable.

- ❌ Myth: "Users create journals from a form."
  ✅ Posting is reachable only via the outbox consumer (`AccountingOutboxProcessor` → `CommerceAccountingService` → `PostJournalAsync`) and internal callers (treasury, sale-update reversal). No user-facing "create journal" endpoint.

- ❌ Myth: "The Ledger owns Treasury / Chart of Accounts."
  ✅ The GL references `AccountId` (`LedgerEntry.cs:35-36`) but does not own the account. Treasury is a separate operational domain; the posting engine enforces treasury *authority* over cash movements but the GL does not own treasury data.

- ❌ Myth: "`Account.CurrentBalance` is the authoritative balance."
  ✅ It is a **denormalized cache**; the invariant states it must equal Σ ledger entries (`Account.cs:14`). Reports recompute from `LedgerEntries` and ignore `CurrentBalance` for truth (`FinancialReportService.cs:19,601-635`).

- ❌ Myth: "Financial statements are pre-computed projections."
  ✅ Reports are **recomputed from `LedgerEntries` every request**; the `GetOrCreateCachedAsync` cache is a no-op pass-through (`FinancialReportsController.cs:279-287`). No projection store exists.

- ❌ Myth: "The party sub-ledger (`LedgerService`/`AccountLedger`) is the General Ledger."
  ✅ They are **separate systems**. `LedgerService` maintains `AccountLedger` + `CustomerTransactions`/`SupplierTransactions` + a scalar `Customer.Balance`/`Supplier.Balance` with flat `RunningBalance = prior + debit − credit` (`LedgerService.cs:218,385`). The GL is `LedgerJournalEntries`/`LedgerLines` with normal-balance-aware `BalanceAfter`. Do not conflate.

- ❌ Myth: "Journal numbers use `SELECT FOR UPDATE`."
  ✅ The code comment says so (`FinancialPostingService.cs:865`) but the implementation uses the `Serializable` transaction + in-tx `JournalNumberSequence.AllocateNext` instead (`:867-894`). No explicit `SELECT … FOR UPDATE`.

- ❌ Myth: "A journal can be deleted/archived/cancelled."
  ✅ ❌ NOT IMPLEMENTED. No such method, state, or endpoint. Deleting a Sale/Purchase with posted journals is blocked and requires reversal instead (`SalesController.cs:1745-1748`, `PurchasesController.cs:1339-1342`).

- ❌ Myth: "Reversal deletes or rewrites the original."
  ✅ Reversal adds a **new** balanced journal (swapped Dr/Cr) and marks the original `Reversed`; both rows persist for audit (`FinancialPostingService.cs:256-359`).

## 17. Final Architecture Conclusion

**Ledger Authority.** The General Ledger is the per-tenant, immutable, double-entry financial record: `JournalEntry` (table `LedgerJournalEntries`, status `Posted`/`Reversed`) plus `LedgerEntry` lines (table `LedgerLines`, exactly one debit XOR credit, each carrying `BalanceAfter`). It is the single source of financial truth. It is **not** the Chart of Accounts and **not** Treasury; it references `AccountId` but owns no account.

**Financial Truth.** Truth = `LedgerJournalEntries` + `LedgerLines` in PostgreSQL. `Account.CurrentBalance` is a denormalized cache maintained only by `FinancialPostingService` via `Account.ApplyEntry`/`ReverseEntry` inside a `Serializable` transaction. All cash movement requires certified-source treasury authority, and `PreventNegative` accounts are balance-checked pre-commit.

**Runtime Flow.** Business op → outbox message (same `ReadCommitted` tx) → `AccountingOutboxWorker`/`Processor` (advisory-locked, version-ordered, idempotent, critical events never terminal-fail) → `CommerceAccountingService` → `FinancialPostingService` (`Serializable`, balanced, authorized, `LedgerMutationScope`-gated) → `JournalEntry`/`LedgerEntry` + balance update → reports recomputed on demand (`RepeatableRead`). Reversal is the only mutation of an existing journal and creates a new balancing journal.

**Aggregate Ownership.** `JournalEntry`+`LedgerEntry` own the immutable financial record and reversal linkage. `JournalNumberSequence` owns numbering. `Account` owns identity/hierarchy/flags and the denormalized balance (mutated only by the engine). `FinancialPostingService` owns posting/validation/treasury-authority/numbering/tx. `FinancialReportService` owns read-model derivation. `AccountingOutboxMessage`+Processor own event transport.

**Transaction Model.** Three scopes: business+outbox in `ReadCommitted`; posting and reversal each in `Serializable` (accounts loaded/ordered by `Id` for deadlock avoidance, idempotency re-checked inside tx, explicit rollback); report reads in `RepeatableRead`. Execution-strategy retry wraps the posting tx. Outbox consumption uses `pg_advisory_xact_lock(tenant, entity)` + claim/lease + exponential backoff; critical financial events never reach terminal failure.

**Projection Strategy.** ❌ There is **no event-sourced projection / materialized statement store** for the GL. Statements are pure functions over `LedgerEntries`, recomputed per request (cache is a no-op pass-through). The outbox is the *posting* event bus, not a *projection* bus. The CommerceHub domain keeps a separate financial transaction ledger reconciled into the tenant GL via `CommerceHubLedgerPosting`.

**Audit Strategy.** Immutability + append-only: every journal retains `PostedAtUtc`, source tracking (`SourceType`/`SourceId`/`SourceReference`), `Description`, `CreatedByUserId`, `IdempotencyKey`, `Status`, and reversal metadata; every line retains `LineNumber`, `LineDescription`, `CreatedAtUtc`, `BalanceAfter`. Nothing is updated or deleted, so the ledger *is* the audit trail.

**Integrity Strategy.** Guaranteed by: immutable journals; unique `(TenantId, IdempotencyKey)` + `(TenantId, JournalNumber)`; DB check constraints `CK_LedgerLines_SingleSide` / `CK_LedgerLines_PositiveAmounts`; `Serializable` posting with ordered account locking; `LedgerMutationScope`; double idempotency check; treasury authority caps; `PreventNegative` projection; and reports that derive truth from `LedgerEntries` (so a corrupted `CurrentBalance` cannot distort statements).

**Gaps (explicitly NOT IMPLEMENTED):**
1. No journal create/edit/delete/archive/cancel/restore UI or API (posting is outbox/treasury/internal only).
2. No journal list/search/filter/paging HTTP surface (`IFinancialPostingService` exposes only get-by-id / by-idempotency-key / exists).
3. No event-sourced projection store; statements recomputed every request (cache no-op).
4. The party sub-ledger (`LedgerService`/`AccountLedger`) is a separate system and must not be conflated with the GL.
5. CommerceHub maintains its own financial ledger, reconciled into the tenant GL — distinct path.
6. Retained earnings / period close absent (see `FLOW-ACC-01`).
