## 0. Critical Orientation: Opening Balance is NOT a Standalone Aggregate

There is **no** `OpeningBalance` entity, `OpeningBalanceController`, `OpeningBalanceService`, `OpeningBalanceDto`, `OpeningBalanceJournal`, or `OpeningBalanceEvent` class in the codebase (searched: `OpeningBalance` as a type prefix returns 0 entity/service/controller types).

Instead, "Opening Balance" is an **entry type within the party sub-ledger** (`AccountLedger` where `TransactionType == TransactionType.OpeningBalance`) plus a **scalar flag** on the party (`Customer.OpeningBalanceAmount`, `Supplier.OpeningBalanceAmount`). The GL journal it generates (supplier only) is an ordinary `JournalEntry` indistinguishable from any other journal after posting.

**Two distinct opening-balance families exist, with ASYMMETRIC accounting treatment:**

| Family | Writes `AccountLedger` (party sub-ledger) | Posts GL Journal (`JournalEntry`) | Posting path |
|---|---|---|---|
| **Customer** opening balance | ✅ Yes (`ApplyCustomerTransaction`) | ❌ **NO** — never enqueued to outbox, never posted to GL | party sub-ledger only |
| **Supplier** opening balance | ✅ Yes (`ApplySupplierTransaction`) | ✅ Yes (via `AccountingOutbox` → `PostSupplierOpeningBalanceAsync`) | outbox → GL |
| **Cashbox** opening float | n/a (cashbox has no `AccountLedger`) | ✅ Yes, via Treasury `CashInAsync` (when not blocked) | treasury → `FinancialPostingService` |
| **Bank** opening balance | ❌ Rejected at `CreateBank` | n/a | treasury-only (creation blocked if non-zero) |

> Status legend used throughout: ✅ Implemented · 🟡 Partially Implemented · ❌ NOT IMPLEMENTED.

## 1. Executive Summary

**What is Opening Balance?**
A one-time, per-party seed of a customer's or supplier's starting AR/AP position (or a cashbox's starting float) recorded before live transactions begin. For customers and suppliers it is materialized as an `AccountLedger` row with `TransactionType.OpeningBalance` plus a `CustomerTransaction` / `SupplierTransaction` and a scalar `OpeningBalanceAmount`/`OpeningBalanceDate` on the party. For suppliers it also emits a GL journal; for customers it does **not**.

**Who owns it?**
- The **party sub-ledger** (`LedgerService` / `AccountLedgers` + `CustomerTransactions`/`SupplierTransactions`) owns the recorded opening-balance entry and the `Party.Balance` scalar.
- The **outbox + `CommerceAccountingService`** owns the supplier GL journal posting.
- The **General Ledger** (`FinancialPostingService`) owns the resulting financial truth for suppliers/cashbox.
- Opening Balance itself owns **none** of these — it is a *transaction type*, not an owner.

**What does it own?**
- Exactly one `AccountLedger` row per party (enforced), carrying `DebitAmount`/`CreditAmount`/`RunningBalance` and the `IsOpeningBalance` flag on the companion `CustomerTransaction`/`SupplierTransaction`.
- The party's `OpeningBalanceAmount` + `OpeningBalanceDate` scalar (a read-only cache, not the source of truth).
- (Supplier only) one GL `JournalEntry` (SourceType `SupplierOpeningBalance`).

**What does it NOT own?**
- It does **not** own the GL engine, `Account.CurrentBalance`, the Chart of Accounts, or Treasury.
- It does **not** own account structure — it references `AccountCodes.OpeningBalanceEquity` (`"3010"`) and `AccountCodes.SupplierPayables` by code.
- It does **not** own the financial truth for *customers* — a customer opening balance is recorded only in the party sub-ledger, with no GL journal.

**What is the financial source of truth?**
- **Supplier opening balance:** the GL `JournalEntry` (after outbox processing). The `AccountLedger` row is the event record; the journal is the truth.
- **Customer opening balance:** the `AccountLedgers`/`CustomerTransactions` party sub-ledger only — there is **no GL representation**. Financial truth for a customer opening balance lives entirely in the party sub-ledger.
- **Cashbox opening float:** the GL journal produced by Treasury `CashInAsync` (when not blocked).
- In all cases `Party.Balance` / `OpeningBalanceAmount` are denormalized caches.

## 6. Aggregate Analysis

| Aggregate | Owns Opening Balance? | Notes |
|---|---|---|
| `AccountLedger` (party sub-ledger) | ✅ is the opening-balance record | One `OpeningBalance` row per party; soft-delete (`IsDeleted`) supported via `IgnoreQueryFilters` |
| `Party` (`Customer`/`Supplier`) | ✅ scalar `OpeningBalanceAmount`/`Date` cache + `Balance` | Not the truth; derived from sub-ledger |
| `JournalEntry` (GL) | 🟡 only for supplier/cashbox | Ordinary journal; no special "opening" aggregate |
| `Account` (CoA) | ❌ | Only referenced by code (`OpeningBalanceEquity`, `SupplierPayables`, `CashFloatReserve`) |
| `PostingRequest` | ❌ | Input DTO; supplier opening balance becomes a `PostingRequest` (`CommerceAccountingService.cs:483`) |
| Opening Balance (as its own aggregate) | ❌ **Does not exist** | There is no `OpeningBalance` aggregate root |

**Conclusion:** Opening Balance is **not** a separate aggregate. It is (a) an `AccountLedger` row of type `OpeningBalance` inside the party-sub-ledger aggregate, and (b) for suppliers, a transient `PostingRequest` that the GL folds into an ordinary `JournalEntry`.

## 7. Behavior

**Creation (customer)** — `CustomersController.SaveCustomerOpeningBalances` (`CustomersController.cs:248-405`):
1. Normalize + hash request; resolve optional mutation `operationId`; claim idempotency `CUSTOMER_OPENING_BALANCE_BATCH` (`CustomersController.cs:259-272`).
2. Load customers; pre-scan `AccountLedgers` for existing `OpeningBalance` per party (`CustomersController.cs:292-299`).
3. Skip duplicate customer entries in batch; skip if `customer.OpeningBalanceAmount.HasValue` or already exists → `Conflict` ("Opening balance already exists for this customer") (`CustomersController.cs:322-326`).
4. Set `customer.OpeningBalanceAmount/Date/BalanceType`; compute debit/credit from `BalanceType` (`CustomersController.cs:328-333`).
5. `await _ledgerService.ApplyCustomerTransaction(...)` → writes `AccountLedger` + updates `Customer.Balance` (`CustomersController.cs:336-344`).
6. Add `CustomerTransaction` with `IsOpeningBalance=true` (`CustomersController.cs:346-361`).
7. **No outbox enqueue, no GL journal.** Complete idempotency record (`CustomersController.cs:377`).

**Creation (supplier)** — `SuppliersController.SaveSupplierOpeningBalances` (`SuppliersController.cs` ~ line 470+) and `StatementOfAccountController.CreateOpeningBalance` (`StatementOfAccountController.cs:263`): identical sub-ledger write **plus** `await _accountingOutbox.EnqueueSupplierOpeningBalanceAsync(tenantId, openingBalanceEntryId)` (`SuppliersController.cs:542`; `StatementOfAccountController.cs:384`). The supplier flow also sets `supplier.OpeningBalanceAmount/Date/BalanceType` and adds a `SupplierTransaction(IsOpeningBalance=true)`.

**Validation rules (runtime):**
- Amount must be > 0 (customer batch: `NormalizeCustomerOpeningBalanceRequest` rejects empty; SOA: `BadRequest` if `<= 0` `StatementOfAccountController.cs:268`).
- Exactly one of debit/credit: `LedgerService` guards; `CommerceAccountingService` throws if both or neither are positive (`CommerceAccountingService.cs:439-449`).
- Duplicate party opening balance → `DuplicateOpeningBalanceException` → HTTP 409 (`LedgerService.cs:342,356`; `CustomersController.cs:383`; `SuppliersController.cs:564`).
- Idempotency: batch-level idempotency record claim (`CUSTOMER_OPENING_BALANCE_BATCH` / `SUPPLIER_OPENING_BALANCE_CREATE`) prevents double-apply on retry (`CustomersController.cs:266-278`; `StatementOfAccountController.cs:282-288`).

**Reading:** UI fetches the party list with `hasOpeningBalance`/`openingBalanceAmount`/`openingBalanceDate` and renders editable rows only for parties without an existing balance (`CustomerOpeningBalance.jsx:23-46`). SOA recomputes opening balance from `AccountLedgers` where `TransactionType.OpeningBalance` (`StatementOfAccountController.cs:136-152`).

**Search / History:** No dedicated opening-balance search API; it is surfaced as part of the party ledger / SOA read models.

**Reset / Reverse / Delete:** NOT IMPLEMENTED (see §5).

## 8. Financial Behavior

**Supplier opening balance → GL journal** (`CommerceAccountingService.PostSupplierOpeningBalanceAsync`, `CommerceAccountingService.cs:423-503`):
- Guard: `PartyType==Supplier`, `TransactionType==OpeningBalance`, exactly one of debit/credit positive.
- Resolve accounts `SupplierPayables` + `OpeningBalanceEquity` (code `"3010"`) via `IAccountResolver.GetByCodesAsync` (`CommerceAccountingService.cs:452-459`).
- **Debit opening balance** (supplier owes us / we owe less):
  - `DR SupplierPayables` (debit amount)
  - `CR OpeningBalanceEquity` (debit amount)
- **Credit opening balance** (we owe supplier):
  - `DR OpeningBalanceEquity` (credit amount)
  - `CR SupplierPayables` (credit amount)
- Builds `PostingRequest` with `SourceType="SupplierOpeningBalance"`, `SourceId=AccountLedger.Id`, `IdempotencyKey="SUPPLIER_OPENING_BALANCE:{tenantId}:{id}"` (`CommerceAccountingService.cs:483-493`).
- Posts via `_postingService.PostJournalAsync` → ordinary balanced `JournalEntry` (`CommerceAccountingService.cs:495`). ✅ Balanced journal (FinancialPostingService enforces Σdebit==Σcredit).

**Customer opening balance → NO GL journal.** It updates `Customer.Balance` and writes `AccountLedger`/`CustomerTransaction` only. There is no `PostCustomerOpeningBalanceAsync` and no outbox enqueue in the customer path.

**Cashbox opening float** (`CashboxController.OpenCashbox`, `CashboxController.cs:335-447`):
- Rule: `request.OpeningBalance` must be `0` → otherwise `BadRequest` `OPENING_FLOAT_TRANSFER_REQUIRED` (`CashboxController.cs:347-354`). So the *open* endpoint itself forbids a non-zero new-cash float.
- If a non-zero float were allowed, it would call Treasury `_treasuryOperationService.CashInAsync(tenantId, cashboxAccountCode, OpeningFloatOffsetAccountCode=CashFloatReserve, amount, ...)` → GL journal (`CashboxController.cs:379-396`).
- **Caveat (Treasury-owned, out of scope but noted):** the current `TreasuryOperationService.CashInAsync` implementation throws `TreasuryValidationException("Direct treasury cash-in is disabled...")` (`TreasuryOperationService.cs:259-273`). So the cashbox opening-float GL path is currently *blocked at the treasury layer*. Whether cashbox opening actually posts today is governed by Treasury, not by Opening Balance.

**Bank opening balance** (`BanksController.CreateBank`, `BanksController.cs:101-135`):
- `if ((request.OpeningBalanceAmount ?? 0m) != 0m) return BadRequest("Bank opening balances must be posted through ledger-backed treasury operations.")` (`BanksController.cs:105-110`). Banks are created with `OpeningBalanceAmount=null`. Bank opening balances, if any, must be posted through Treasury operations, not at creation.

**Current Balance / BalanceAfter:**
- Party sub-ledger: `AccountLedger.RunningBalance = priorBalance + debit − credit` (`LedgerService.cs:218,231`). `CustomerTransaction.BalanceAfter` / `SupplierTransaction.BalanceAfter` captured from `Apply*Transaction` return (`CustomersController.cs:356`).
- GL: supplier journal posts to `LedgerEntries`; `Account.CurrentBalance` is a cache updated by `FinancialPostingService` (FLOW-ACC-04). Opening Balance does not directly mutate `Account.CurrentBalance`.

**PreventNegative:** No dedicated "prevent negative opening balance" rule found. Amount must be > 0; sign is carried by `BalanceType` (Debit/Credit). Party `Balance` can be negative (credit balance) by design.

## 9. Constraints (implementation-backed business rules)

1. **Only one opening balance per party.** `EnsureOpeningBalanceNotAlreadyAppliedAsync` checks in-flight + persisted `AccountLedgers` (`TransactionType.OpeningBalance`) and throws `DuplicateOpeningBalanceException` (`LedgerService.cs:319-358`). Controllers additionally short-circuit if `Party.OpeningBalanceAmount.HasValue` (`CustomersController.cs:322`; `SuppliersController.cs:484`; `StatementOfAccountController.cs:319`).
2. **Cannot duplicate (idempotency).** Batch idempotency record claim (`CUSTOMER_OPENING_BALANCE_BATCH`, `SUPPLIER_OPENING_BALANCE_CREATE`, `SUPPLIER_OPENING_BALANCE:{...}` outbox key) (`CustomersController.cs:266`; `StatementOfAccountController.cs:282`; `AccountingOutboxService.cs:176`).
3. **Must be positive amount.** `Amount <= 0` rejected (`StatementOfAccountController.cs:268`; customer normalization).
4. **Exactly one of debit/credit.** Both-zero or both-positive rejected (`CommerceAccountingService.cs:439-449`).
5. **Tenant isolation.** Every write filters/sets `TenantId`; outbox processor re-checks `tenantId` and reloads `AccountLedger` under the same tenant (`AccountingOutboxProcessor.cs:1708-1725`). `ITenantOwned` enforced.
6. **Supplier journal must be balanced.** Enforced by `FinancialPostingService.PostJournalAsync` (FLOW-ACC-04); the two lines are always equal-and-opposite by construction (`CommerceAccountingService.cs:461-481`).
7. **Bank opening balance not at creation.** Non-zero rejected; must go through treasury (`BanksController.cs:105`).
8. **Cashbox opens with zero new cash.** Non-zero float rejected with `OPENING_FLOAT_TRANSFER_REQUIRED` (`CashboxController.cs:347`).
9. **No edit / reverse / reset / delete** of an existing opening balance (see §5).
10. **Customer opening balance has no GL representation** — a hard asymmetry, not a configurable rule.

## 10. SQL Transactions

- **Customer batch:** controller opens `BeginTransactionAsync` (`CustomersController.cs:267`); idempotency claim; writes `AccountLedger`+`CustomerTransaction`+`Customer` scalar inside it; `CompleteFinancialMutationResultAsync` commits (`CustomersController.cs:377`). On `DuplicateOpeningBalanceException` it clears change tracker, re-attaches idempotency record, returns 409; on other errors rolls back (`CustomersController.cs:383-404`).
- **Supplier batch:** same pattern; plus outbox enqueue is part of the same unit of work (`SuppliersController.cs:267,542,558`). `DuplicateOpeningBalanceException` → clear tracker, 409 (`SuppliersController.cs:564-583`); other errors → `transaction.RollbackAsync` (`SuppliersController.cs:586`).
- **LedgerService.Apply*Transaction:** if no ambient transaction, opens its own `ReadCommitted` transaction; commits before returning; rolls back on `DuplicateOpeningBalanceException` (treated as expected 409) or other errors (`LedgerService.cs:208-277`).
- **Outbox processing (supplier):** `AccountingOutboxProcessor.ProcessSupplierOpeningBalanceAsync` uses `db.Database.CreateExecutionStrategy()` (EF retry strategy) and an explicit `BeginTransactionAsync`; posts via `PostSupplierOpeningBalanceAsync` (which internally calls `PostJournalAsync` inside its own `Serializable` GL transaction per FLOW-ACC-04); commits on success, rolls back on failure (`AccountingOutboxProcessor.cs:1693-1755`).
- **Isolation:** controller/ledger transactions use `ReadCommitted`; the GL `PostJournalAsync` uses `Serializable` (FLOW-ACC-04). 
- **Concurrency:** party row locked via `LockPartyForUpdateAsync` before balance mutation (`LedgerService.cs:215,122`) to serialize concurrent opening-balance writes.
- **Atomicity:** sub-ledger write + party scalar + (supplier) outbox enqueue are atomic within the controller transaction. GL journal posting is a separate, later, idempotent outbox consumer transaction.
- **Retries:** outbox consumer wrapped in execution strategy (retry on transient failures); idempotency key prevents double journal on replay (`AccountingOutboxProcessor.cs:1693`).
- **Rollback:** explicit `transaction.RollbackAsync` on every failure path; change-tracker cleared on duplicate conflict to avoid partial commit (`SuppliersController.cs:572`).

## 11. Events

- **Outbox (supplier only):** `AccountingOutboxService.EnqueueSupplierOpeningBalanceAsync` writes an `AccountingOutboxMessages` row: `MessageType="SupplierOpeningBalance"`, `BusinessEntityId=openingBalanceId`, payload `{ OpeningBalanceId }`, `IdempotencyKey="SUPPLIER_OPENING_BALANCE:{tenantId}:{id}"` (`AccountingOutboxService.cs:174-179`).
- **Consumer:** `AccountingOutboxProcessor` dispatches `"SupplierOpeningBalance"` → `ProcessSupplierOpeningBalanceAsync` (`AccountingOutboxProcessor.cs:57,723,1685`); reloads the `AccountLedger`, calls `CommerceAccountingService.PostSupplierOpeningBalanceAsync`, which posts the GL journal.
- **Customer:** NO outbox event. Customer opening balances emit no `AccountingOutboxMessage` and no GL event.
- **Synchronization:** supplier GL journal is synced to the ledger asynchronously via the outbox→processor pipeline (same as sales/payments). The `AccountLedger` row is written synchronously; the `JournalEntry` is written by the background consumer.
- **No dedicated "OpeningBalancePosted" domain event / projection** exists beyond the generic outbox message. Reports read the ledger/sub-ledger directly.

## 12. Runtime Architecture

**Supplier opening balance (full GL path):**
```
POST /suppliers/opening-balances  (or /soa/opening-balance)
  ↓

  ↓

  ↓

  ↓  [background consumer]

  ↓
CommerceAccountingService.PostSupplierOpeningBalanceAsync
  ↓  (resolve SupplierPayables + OpeningBalanceEquity "3010")
FinancialPostingService.PostJournalAsync  →  LedgerJournalEntries + LedgerLines (SourceType=SupplierOpeningBalance)
  ↓
Account.CurrentBalance cache updated (by posting engine)
  ↓
Reports read from LedgerEntries (FLOW-ACC-04)
```

**Customer opening balance (party sub-ledger only — NO GL):**
```
POST /customers/opening-balances
  ↓

  ↓
LedgerService.ApplyCustomerTransaction  →  AccountLedger (OpeningBalance) + Customer.Balance
  ↓

  ↓

```

  ↓

## 15. Canonical Pattern

Opening Balance is a **party-sub-ledger entry type**, not an aggregate. Its canonical shape:
1. A controller accepts a batch of party opening balances, claims an idempotency record, and validates amount/duplicate.
2. `LedgerService.Apply*Transaction` writes a single `AccountLedger` row (`TransactionType.OpeningBalance`), updates the party `Balance` scalar, and adds a `CustomerTransaction`/`SupplierTransaction` with `IsOpeningBalance=true` — all inside one DB transaction.
3. **Supplier only:** the `AccountLedger.Id` is enqueued to the `AccountingOutbox`; a background consumer translates it via `CommerceAccountingService.PostSupplierOpeningBalanceAsync` into a balanced GL `JournalEntry` (DR/CR `SupplierPayables` ↔ `OpeningBalanceEquity 3010`) through `FinancialPostingService`.
4. **Customer:** no GL journal — the opening balance exists solely in the party sub-ledger.
5. Cashbox/Bank floats are Treasury-owned and post (or are blocked) at the treasury layer, not via the party sub-ledger.

## 16. Documentation Validation (implementation misconceptions corrected)

❌ "Opening Balance is a standalone entity/aggregate with its own controller and service."
✅ It is an `AccountLedger` row of `TransactionType.OpeningBalance` plus a party scalar; no `OpeningBalance` type exists.

❌ "Opening Balance posts directly to account balances."
✅ Supplier OB posts through `FinancialPostingService` (via outbox→`CommerceAccountingService`); the party `Balance` is updated by `LedgerService`, not by the OB code directly touching GL.

❌ "Opening Balance owns the Ledger / General Ledger."
✅ The GL owns the financial truth. OB (supplier) only *creates a journal*; it does not own the ledger.

❌ "Every opening balance creates a GL journal."
✅ Only **supplier** (and cashbox/bank via treasury) opening balances reach the GL. **Customer** opening balances never post a journal — there is no `PostCustomerOpeningBalanceAsync`.

❌ "Opening Balance can be edited / reversed / reset."
✅ NOT IMPLEMENTED. It is immutable once written; only a future adjustment changes the running balance.

❌ "You can have multiple opening balances per party."
✅ Exactly one per party, enforced by `EnsureOpeningBalanceNotAlreadyAppliedAsync` + scalar check → 409.

❌ "Opening Balance becomes indistinguishable from normal journals after posting."
✅ Only true for **supplier** (ordinary `JournalEntry`, `SourceType=SupplierOpeningBalance`). For **customer**, there is no journal at all — it remains only in the party sub-ledger.

❌ "Bank opening balance is set at bank creation."
✅ Rejected; non-zero `OpeningBalanceAmount` at `CreateBank` returns 400; banks must use treasury operations.

## 17. Final Architecture Conclusion

**Opening Balance Authority:** The party sub-ledger (`LedgerService` + `AccountLedgers`/`*Transactions`) is the authority for *recording* an opening balance. The `AccountingOutbox` + `CommerceAccountingService` is the authority for *translating* a supplier opening balance into GL. Treasury is the authority for cashbox/bank floats. Opening Balance itself holds no authority.

**Financial Truth:**
- Supplier opening balance → GL `JournalEntry` (after outbox).
- Customer opening balance → party sub-ledger only (no GL).
- Cashbox/bank float → Treasury → GL (when not blocked).
- Party `Balance` / `OpeningBalanceAmount` are always denormalized caches.

**Runtime:** Controller (validate + idempotency + write sub-ledger) → [supplier] outbox enqueue → background consumer → `CommerceAccountingService` → `FinancialPostingService.PostJournalAsync` (Serializable GL transaction).

**Aggregate Ownership:** Opening Balance is NOT its own aggregate. It lives inside the party-sub-ledger aggregate (`AccountLedger`) and, for suppliers, becomes a transient `PostingRequest` folded into the GL aggregate (`JournalEntry`).

**Transaction Model:** ReadCommitted controller/ledger transactions; Serializable GL posting transaction inside the outbox consumer; EF execution-strategy retry; explicit rollback on every failure path; party row lock (`LockPartyForUpdateAsync`) for concurrency.

**Projection Strategy:** No event-sourced projection for opening balance. Reports/SOA recompute opening balance by filtering `AccountLedgers`/`*Transactions` where `TransactionType.OpeningBalance` (FLOW-ACC-04 reports read the GL directly). The outbox→GL pipeline is the only async projection.

**Integrity Strategy:** One-per-party enforced by `EnsureOpeningBalanceNotAlreadyAppliedAsync` (in-flight + persisted) plus scalar `HasValue` check → `DuplicateOpeningBalanceException` → 409. Idempotency records (batch) + outbox idempotency key (supplier) prevent double application on retry. Tenant isolation enforced on every read/write.

**Audit Strategy:** Opening balance writes are captured via `CustomerTransaction`/`SupplierTransaction` (`IsOpeningBalance=true`, `ReferenceNumber`, `Notes`, `CreatedAt`) and the `AccountLedger` row (tenant, party, doc number, amounts, `UserId`). Cashbox open is logged via `LogCashboxAuditAsync` (`CashboxController.cs:412`) including `journalId`/`journalNumber` when a float posts. No dedicated opening-balance audit report exists.
